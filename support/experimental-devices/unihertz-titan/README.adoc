= Original Unihertz Titan feasibility prototype

This directory implements the build-only part of M0/M1 in
link:../../../doc/porting-plans/unihertz-titan.adoc[the porting plan].
It was prepared with OpenAI Codex assistance for this fork. It is an isolated
experiment, not a supported device under `devices/` or an upstream submission.
Titan Pocket, Slim, 2 and 2 Elite are different devices.

The owner has an original Titan running Ubuntu Touch with Nix installed.
Supplied runtime evidence identifies the eMMC variant, Linux `4.14.141+`, and
32 MiB boot/recovery partitions matching the reference image's capacity
requirement. Reported Android system/vendor builds are recorded in the inventory;
the uploaded kernel configuration matches the reference build's recorded hash.
Restore provenance and recovery procedure still need verification. Build and
image-format results below do not establish that an image boots or that any
hardware works under NixOS.

== What this builds

* The pinned UBports Linux 4.14.141 kernel with `titan_defconfig halium.config`,
  Android Clang r353983c and the matching Android GCC 4.9 cross toolchains.
* A reproduction of the Ubuntu Touch reference boot-image recipe, using the
  pinned Ubuntu Touch initramfs, adaptation overlay and prebuilt Titan DT table.
* A separate source-built AArch64 rescue ramdisk with a small independent
  PID 1 and static backup tools, plus separate experimental USB acquisition and
  USB probe profiles. None has phone boot validation; see the build-only
  sections below.
* Host-side inventory, kernel configuration comparison, read-only kernel API
  probes, boot-image inspection and bounded private boot/recovery/dtbo
  acquisition tools, bounded GPT capture/validation, and a host-only sparse ext4
  archive verifier, with
  automated tests.
* A link:entry-return-trial.adoc[bootloader entry and return trial] with a
  fastboot helper that sends only fixed read-only queries or one return command.
  The owner approved it, and it ran once on 2026-10-15: the phone entered
  bootloader fastboot, the Mac recognized it, and `fastboot reboot` returned to
  Ubuntu Touch.
* A link:temporary-boot-trial.adoc[temporary (RAM) boot trial]. Stage A ran
  once on 2026-10-15: the bootloader accepted a `fastboot boot` of the phone's
  own boot image, then crashed and reset into a normal boot from storage; an
  ordinary reboot afterwards was normal. Stage B crashed the bootloader the
  same way with a compact self-rebooting probe image, so temporary boot through
  `fastboot boot` is not available.
* A link:recovery-route-trial.adoc[recovery-partition probe trial], run once
  on 2026-10-15 with the owner's approval: `fastboot flash` wrote the probe
  into recovery, a Volume Up start ran it on the phone, its deadline restart
  reached fastboot, and the original recovery was restored byte for byte.
* An link:control/README.adoc[offline control-region acquisition image] and
  its link:control-acquisition-trial.adoc[trial], run on 2026-10-15 with the
  owner's approval. Started from the recovery partition, it copied the sixteen
  regions other than `userdata` to the Mac, each read twice, stable and
  consistent, then restarted into fastboot, and the original recovery was
  restored. The first attempt stalled in macOS's serial driver; the repeat
  succeeded.
* A link:repo-kernel-trial.adoc[repository-kernel probe trial], run on
  2026-10-15 with the owner's approval: the kernel this repository builds booted
  from the recovery partition, ran the probe, which reported kernel `4.14.141`,
  restarted into fastboot, and the original recovery was restored. This passes
  M1's hardware gate for the kernel.
* The link:native-n0.adoc[native route's N0 record], after the owner chose the
  native route on 2026-10-15: the pinned postmarketOS MT6771 starting point,
  the Titan's hardware facts, a gap table and a bounded first-boot scope.
* The link:native-boot-trial.adoc[first native-route boot], run on
  2026-10-15 with the owner's approval: Linux 7.3-rc3 with a Titan device tree
  and bootloader overlay (`native/`) booted from the recovery partition, and
  the probe, built for modern device naming, reported kernel `7.3.0-rc3` after
  guarding the eMMC and binding USB device mode. The phone then restarted into
  Ubuntu Touch, and the original recovery was restored.
* The link:native-diag-trial.adoc[native-route diagnostic trial], run on
  2026-10-16 with the owner's approval: the same modern kernel, with the
  link:diag/README.adoc[diagnostic ramdisk], sent its complete log, the device
  tree the bootloader passed and a device-driver table to the Mac, reading
  nothing from storage. The bootloader applied the image's own overlay; all
  eight CPUs, the eMMC, USB, the PMIC regulators and the GPU came up. The
  original recovery was restored.
* The link:consistent-preservation.adoc[remaining consistent preservation
  requirements] and the link:userspace-feasibility.adoc[kernel/userspace
  feasibility record].
* A fixed link:control-region-preservation.adoc[normal-mode reader] for the
  twelve unmounted control and calibration regions. One verified private copy
  exists; it is stable, not consistent.
* A separate fixed-scope link:bootloader-preservation.adoc[LK partition reader]
  for private passive bootloader inspection. It does not enter fastboot or
  establish that either bootloader copy is a working fallback.
* A fixed-scope link:os-partition-preservation.adoc[vendor/system reader] with
  guarded process mount views, bounded streaming and sparse private Mac output.
* A fixed 225 MiB link:firmware-preservation.adoc[firmware/boot-area reader]
  covering fourteen further GPT regions and both separate eMMC boot areas.
* A host-only link:backup-catalog.adoc[private backup catalog verifier] that
  rehashes the retained copies, checks layout agreement and records coverage gaps.

The reference image retains Ubuntu Touch's command line and userspace contract.
It is not a NixOS initramfs or root filesystem. Current Mobile NixOS uses a
systemd baseline requiring a newer kernel; choosing a compatible stage 1 and
stage 2 remains a separate feasibility decision. Direct USB probes now confirm
missing pidfd/close-range interfaces and statx mount metadata used by systemd
261; see link:hardware-inventory.adoc#_direct_kernel_api_measurements[the API audit].
The generic Android image builder and existing devices are unchanged.

== Build and inspect

Use an x86_64 Linux Nix builder for the kernel and reference image. The original
Android compiler prebuilts are x86_64 host executables; this expression is not a
native kernel build on the phone or Mac. The `tests` target uses a deliberately
nonbootable kernel fixture and native packaging tools, so it also supports macOS.
All targets use the repository's existing Nixpkgs pin through `pkgs.nix`.

[source,sh]
----
# From the repository root:
nix-build support/experimental-devices/unihertz-titan -A tests --no-out-link
nix-build support/experimental-devices/unihertz-titan -A kernel --no-out-link
nix-build support/experimental-devices/unihertz-titan -A referenceBootImage --no-out-link
----

The kernel output includes `Image`, `Image.gz`, the final `config`, `vmlinux`,
`System.map`, modules and build information. Preserve the configuration and
hashes with any later hardware test. A repeat build from a separate clean store
is required before claiming bit reproducibility.
Kernel modules remain in the kernel output; this prototype does not construct
or update the Ubuntu Touch root filesystem. Any eventual boot test must account
for matching root-filesystem and vendor modules as well as the boot image.

To inspect an image without Nix, use Python 3:

[source,sh]
----
python3 support/experimental-devices/unihertz-titan/tools/inspect-boot-image.py \
  --json --check-titan /absolute/path/to/boot.img
----

`--check-titan` checks the reference geometry, including the 32 MiB final image
and AVB footer. Generic inspection without this flag can inspect intermediate
unsigned images. The inspector checks bounds and metadata consistency; it does
not verify cryptographic signatures, the bootloader's trust policy or bootability.

== Build-only rescue userspace

`rescue.ramdisk` builds `initramfs.cpio.gz` and an inspectable `root/` tree on an
x86_64 Linux builder. Its AArch64 executables use static musl: an independent
MIT-licensed PID 1, a minimal BusyBox 1.37.0, e2image 1.47.4 and Zstandard 1.5.7.
Sources and patches come from the existing Nixpkgs pin. The build rejects ELF
interpreter or shared-library dependencies and records payload/archive hashes.
No Ubuntu Touch ramdisk binary, systemd, firmware or Nix store is packed.

PID 1 mounts devtmpfs, read-only proc/sysfs and bounded RAM-backed `/run` and
`/tmp`. It checks that these and the RAM root are the complete mount set. For
every visible block node it matches sysfs/device numbers, sets `BLKROSET`, and
verifies `BLKROGET`. It waits up to ten seconds until the fixed `mmcblk0` disk and
exactly its 38 measured partitions, both eMMC boot areas and the RPMB node are
guarded with no device still registering; RAM, loop and zram nodes are guarded
but never count as storage. It then checks
mounts and block protection every second. A failure prints a marker and waits
indefinitely; the vendor kernel's own watchdog and panic handling still apply. It starts no shell, USB/network service, Android/modem
service, filesystem repair, acquisition, or automatic reboot.

`TITAN_RESCUE_READY` means the expected eMMC block devices were present and
every visible block node passed those guards. It does not stop
firmware/kernel writes or establish a consistent calibration snapshot. Devices
can arrive between scans. A 2026-10-15 audit fixed a premature readiness rule
under which the built-in `zram0` counted as storage. This default profile's own
mount check ignores mount IDs; the separate USB acquisition build's guards
rejected mount ID 0, see link:source/README.adoc[the source guard]. VM builds
substitute the virtio disk `vda` with no partition count, so the production
readiness rule has not run anywhere. The production ramdisk contains no VM callback or shutdown path.

[source,sh]
----
nix-build support/experimental-devices/unihertz-titan -A rescue.ramdisk --no-out-link
nix-build support/experimental-devices/unihertz-titan -A rescue.toolTests --no-out-link
nix-build support/experimental-devices/unihertz-titan -A rescue.vmTests --no-out-link
----

The tool checks execute the AArch64 binaries under qemu-user against a synthetic
ext4 image, stream it through e2image/Zstandard, and check the restored filesystem
and payload. This uses the builder's kernel. The VM checks compile the same
PID 1 core for x86_64 with a separate test callback and boot the pinned Linux
6.18.38 kernel under networkless QEMU TCG. A VM-only bootstrap loads its virtio
modules before execing PID 1. The three cases cover read-only protection of a
writable host fixture, an incorrect sentinel, and missing storage; negative
cases must remain running until the host terminates them. Disk hashes must
remain unchanged. These tests do not exercise the Titan's 4.14 kernel or hardware.

This output is a ramdisk, not a flashable Android boot image or a demonstrated
recovery environment. USB transport, exact storage identity/completeness,
watchdog/charging behavior and an authorized boot/return route still need
validation. See link:recovery-preparation.adoc[the recovery record]. Keep built
payloads and raw diagnostics outside Git; no phone mode change is part of these
commands.

== Off-device serial transport prototype

`transport.sender` builds a separate static AArch64 sender with pinned OpenSSL
3.6.3 for SHA-256; `transport.nativeSender` builds the corresponding Linux host
fixture. Neither is included in `rescue.ramdisk` or started by its PID 1.
The Python receiver and exact
link:transport/protocol.adoc[TTR1 wire contract] live in `transport/`.

The protocol binds every frame to a random host nonce, bounds chunks and total
bytes, rejects sequence/hash mismatches, and requires a host acknowledgement
followed by a matching sender receipt. The host saves to a new private staging
file, fsyncs it and independently verifies its contents before acknowledging.
Missing completion leaves an incomplete staging file. The nonce is not peer
authentication, and a successful transfer does not establish source consistency.

The sender accepts only already-open local read-only regular files or pipes;
the host cannot request paths, commands or partitions. Streamed input additionally
requires a separate local producer-status pipe. The separate
link:producer/README.adoc[producer prototype] exercises pipeline supervision
against regular ext4 image files, including e2image read-error diagnostics with
exit status zero. The separate link:block/README.adoc[guarded block producer]
adds the fixed userdata source profile. The separate
link:usb-pipeline/README.adoc[USB acquisition profile] integrates these pieces
for build-only review and disposable VM validation.

Limits apply to transmitted bytes, so a future compressed sparse acquisition can
stream without retaining userdata in RAM or reserving its entire logical size
on the Mac. The receiver checks free space incrementally and preserves a 64 MiB
reserve; this is not a guarantee that a particular archive will fit.

[source,sh]
----
# x86_64 Linux builder; synthetic sockets, PTYs, files and pipes only.
nix-build support/experimental-devices/unihertz-titan -A transport.sender --no-out-link
nix-build support/experimental-devices/unihertz-titan -A transport.tests --no-out-link

# Host receiver fixtures, without executing a sender binary or using real USB.
PYTHONDONTWRITEBYTECODE=1 python3 support/experimental-devices/unihertz-titan/transport/test_transport.py
----

The receiver's explicit TTY interface is for later integration. Do not point it
at the running phone: no ACM gadget, phone source supervisor or boot/return
route has been established. Actual USB enumeration, peer readiness and
acquisition quiescence remain separate requirements. Keep artifacts and diagnostics private.

== Off-device imaging/compression supervisor

`producer.supervisor` builds a separate static AArch64 pipeline supervisor with
fixed `/bin/e2image` and `/bin/zstd` paths. It accepts already-open read-only
regular filesystem images and separate write-only data/status pipes. It validates the
primary superblock and source geometry, concurrently drains compressed output
and both diagnostic streams, and checks child exits and source stability before
emitting the transport's success status. It is not part of rescue PID 1.

The link:producer/README.adoc[producer contract] records the complete checks and
limitations. `producer.tests` exercises a generated filesystem through producer,
sender, receiver, sparse decompression and read-only filesystem/payload checks.
Separately compiled test variants allow synthetic failing executables; the
production binary rejects those overrides. No phone block device, live userdata
copy or recovery boot is part of these tests.

== Build-only storage-source preflight

`storage.checker` builds a standalone static AArch64 checker for the measured
userdata layout. It verifies kernel/sysfs identities and geometry, read-only
block flags, mount/swap state and holders, while retaining a read-only exclusive
partition descriptor across repeated checks. It does not read partition contents
or change storage flags. Its fixed production profile has no runtime overrides.

The link:source/README.adoc[preflight contract] explains the retained-descriptor
API and the limits of Linux block claims. The checker closes its descriptors on
exit; its success cannot authorize a later separate acquisition. The separate
block producer below uses the library API to retain its own checked descriptors.
The standalone checker is not started by rescue PID 1.

`storage.vmTests` uses the same guard with a separate fixed virtio profile and
generated sparse GPT disks in disposable x86_64 guests. Neither the test profile
nor its fault-injection/poweroff callback enters the production checker. These
checks do not establish GPT integrity, writer quiescence or Titan runtime support.

== Build-only guarded block acquisition

`acquisition.producer` combines the fixed userdata guard with the imaging and
compression supervisor in a separate static AArch64 executable. It accepts
only output/status pipe descriptors, a compressed-byte limit and a deadline.
It retains the checked exclusive partition descriptor through child cleanup,
repeated source checks and status EOF. The caller cannot override its source
or helper executable paths. This standalone target does not supply startup; the
separate `usbAcquisition.ramdisk` experiment below provides a fixed PID 1 launcher.

The link:block/README.adoc[block acquisition contract] describes its preflight,
completion rules and remaining consistency limits. `acquisition.vmTests` runs
five generated GPT/ext4 fixtures through a separate x86_64 VM profile, the real
imaging/compression tools, sender and host receiver. It includes sparse restore,
filesystem/payload verification, specific failure results and complete disk
hashes before and after each guest. The emulated second serial port is a test
transport; it does not establish Titan USB operation or a recovery route.

== Disposable VM USB startup fixture

`usb.vmTests` uses real Linux configfs ACM, `dummy_hcd` and host `cdc_acm` inside
a networkless x86_64 VM. The separate link:usb/README.adoc[USB lifecycle fixture]
checks raw gadget readiness before binding, host enumeration, binary transfers
and explicit disconnect/cleanup with fixed synthetic descriptors. It uses no
phone or physical USB passthrough and does not execute block acquisition.
All five cases passed with Linux 6.18.38 on 2026-10-15; the Mac independently
verified all downloaded fixture disks against their unchanged before/after hashes.

The callback temporarily owns a visible configfs mount after the existing
rescue guard's VM handoff. The default `rescue.ramdisk` and source checker keep
their original six-mount policy. The separate integrated profile below uses an
explicit seven-mount policy and owns the full acquisition lifetime.

== Build-only USB acquisition profile

`usbAcquisition.ramdisk` builds a separate static AArch64 initramfs with a fixed
ACM owner, guarded userdata producer, sender, `e2image` and Zstandard. It uses the
measured MTU3 device/driver path, sets and retains raw `ttyGS0` before binding,
then seals its visible configfs mount read-only before starting acquisition.
The explicit USB source profile accepts exactly seven RAM/virtual mounts; it
never falls back to the default six-mount policy. See the
link:usb-pipeline/README.adoc[full lifecycle, limits and VM contract].

[source,sh]
----
nix-build support/experimental-devices/unihertz-titan -A usbAcquisition.ramdisk --no-out-link
nix-build support/experimental-devices/unihertz-titan -A usbAcquisition.toolTests --no-out-link
nix-build support/experimental-devices/unihertz-titan -A usbAcquisition.vmTests --no-out-link
nix-build support/experimental-devices/unihertz-titan -A mountPolicy.vmTests --no-out-link
----

After transfer starts, production retains the gadget even on failure: sender
exit or an empty software queue cannot prove that its final bytes reached the
Mac. Worker cancellation must reap all children before any pre-transfer cleanup.
The VM-only receipt channel permits teardown after the host has verified a
complete archive or confirmed an incomplete result. It is absent from the
AArch64 artifact. This output is not an Android boot image, a consistent Titan
backup or a demonstrated recovery environment. Hardware boot/exit, writer
quiescence, calibration preservation and Mac USB recognition remain unverified.

== Build-only USB probe profile

`usbProbe.ramdisk` holds only the rescue PID 1 built with a probe profile for a
first temporary boot. It guards every block device read-only, binds the same
fixed ACM gadget, writes one bounded status line every two seconds and reboots
by itself at a fixed deadline from a separate process, with a PID 1 backstop.
It reads no storage contents, accepts no input and starts no acquisition. See
the link:usb-probe/README.adoc[probe record] and Stage B of the
link:temporary-boot-trial.adoc[temporary boot proposal].

[source,sh]
----
nix-build support/experimental-devices/unihertz-titan -A usbProbe.ramdisk --no-out-link
nix-build support/experimental-devices/unihertz-titan -A usbProbe.toolTests --no-out-link
nix-build support/experimental-devices/unihertz-titan -A usbProbe.vmTests --no-out-link
----

== Private rescue boot-image packaging

The local link:rescue-image.adoc[rescue-envelope helper] combines the exact
preserved installed kernel and DTB with the reviewed USB acquisition ramdisk.
It checks fixed input hashes and emits a raw, unsigned Android v2 envelope in a
new private directory outside Git and the Nix store. It replaces Ubuntu Touch
startup arguments, recomputes the legacy image checksum and discards the old
AVB metadata. The generic format check is separate from bootloader acceptance;
no flashing or temporary-boot command is supplied.

The private result is 12707840 bytes and matches the pinned Android assembler
byte-for-byte. Its kernel and DTB match the preserved installed boot, and its
ramdisk is the reviewed AArch64 USB acquisition build `27d2a3da...`. An x86_64
VM variant of those sources passed; the AArch64 binaries ran only qemu-user
refusal checks. At commit `bae47c7a`, all 186 host tools tests and the packaging
fixture passed on the Mac. That embedded ramdisk contains the mount-ID-0 and
zram defects found on 2026-10-15, so that envelope must not be used. The same
helper then packaged the final corrected ramdisk `0ed6d547...` into a
12707840-byte envelope `52f48e74...`, again byte-identical to the pinned
assembler; see
link:rescue-image.adoc[the envelope record]. Both remain unsigned and untested on
hardware; packaging does not establish a recovery route.

The adaptation's `unihertz-titan.dtb` is a 112135-byte Android DT table containing
one 112071-byte flattened device tree at offset 64. On 2026-10-15 its SHA-256,
`51a6baed...`, matched the installed boot's DTB. It is not a raw FDT starting
at byte zero. Header-v2 packing uses a separate DTB section and `Image.gz`;
appending a DTB to the kernel or using the legacy `--dt` option is not equivalent.

The reference recipe first adds an AVB hash footer, then appends the downloaded
GSI vbmeta image. Inspection must describe the final metadata; it must not claim
the earlier hash descriptor remains in the final vbmeta. Matching this recipe
does not prove that the owner's installed firmware accepts it.

The source pins document provenance, not a complete redistribution audit.
Before publishing binary images or firmware, resolve the adaptation's included
binaries, initramfs components and vendor firmware terms. Device backups,
identifiers, authentication keys and raw collected logs belong outside Git.

Two helper rebuild tasks remain open:

* The adaptation ships an AArch64 glibc `uinput-titan` executable and a service,
  without matching source/build instructions in the pinned tree. A

  kernel enables `CONFIG_COMPAT=y` and `CONFIG_BINFMT_ELF=y`. Replace or reproduce
  this helper explicitly when constructing a NixOS initramfs; do not assume it
  is an AArch64 binary.

== First userspace configuration audit

The merged reference configuration produced on 2026-10-14 has SHA-256
`1113327761998175c8cc78dbce10ac23c7fed8a8418f1072e553e8c0acc4286b`.
The owner's subsequently uploaded configuration has exactly the same decompressed
hash and 4000 parsed settings; see the
link:hardware-inventory.adoc#_running_kernel_configuration[runtime audit].
This matches configuration contents without establishing identical kernel
binaries or source revisions. The findings below apply to the supplied runtime
configuration as well as the reference build.

[cols="2,3",options="header"]
|===
|Reference setting |Consequence for a later NixOS experiment
|`FHANDLE=n`
|Violates systemd 261's explicit requirement for libudev and mount handling.
  Mobile stage 1 also uses systemd's udev.
|`ANDROID_PARANOID_NETWORK=y`
|Conflicts with Mobile's required configuration; Android-specific restrictions
  need to be removed before testing ordinary non-root Linux networking.
|`TMPFS_POSIX_ACL=n`, `TMPFS_XATTR=n`, `EXT4_FS_POSIX_ACL=n`
|Missing filesystem features required by Mobile's kernel configuration.
|`FW_LOADER_USER_HELPER=y`, `FW_LOADER_USER_HELPER_FALLBACK=y`
|systemd does not provide the old firmware-loading helper. Audit driver reliance
  and provide firmware using a tested kernel loading path.
|`NF_TABLES=n`
|Cannot provide the nftables functionality requested by current Mobile.
|`CGROUP_PIDS=n`
|The PIDs cgroup controller's task-count accounting and limits are unavailable.
  This alone is not a PID-1
  boot blocker: systemd permits cgroups without individual controllers.
|===

Modules, devtmpfs, VT, namespaces (including user namespaces), seccomp/filter,
TUN, ext4, tmpfs, configfs USB gadget, evdev and uinput are already enabled.
`DEVTMPFS_MOUNT=n` does not prevent early userspace from mounting devtmpfs itself.
`RD_GZIP=y` matches Mobile's default initramfs compression; `RD_XZ=n` matters only
if choosing XZ. `FRAMEBUFFER_CONSOLE=n` leaves a kernel console gap, without
establishing whether userspace framebuffer graphics work.
The merged configuration also has `CONFIG_BT=n` and `CONFIG_MTK_COMBO_BT=y`.
Bluetooth suboptions requested by `halium.config` do not establish standard
Linux Bluetooth support when their parent is disabled. The supplied runtime
configuration confirms these settings; inspect the actual driver interfaces
before designing a BlueZ or Android Bluetooth bridge.

Sources: link:https://github.com/systemd/systemd/blob/v261/README[systemd 261 requirements],
link:../../../modules/kernel-config.nix[Mobile kernel configuration], and
link:../../../modules/initrd.nix[Mobile early userspace].
Fixing flags does not resolve the separate Linux 4.14 versus systemd 261's
supported Linux 5.10 baseline. Audit actual backports and select a compatible
userspace or a newer kernel before attempting M2.

Use `tools/compare-kernel-config.py` to compare a collected configuration with
this reference output; see the
link:hardware-inventory.adoc#_compare_the_running_kernel_configuration[inventory procedure].
The comparison keeps missing symbols distinct from disabled settings, hashes
uncompressed configuration contents and limits printed values to a fixed list
of 50 boolean/tristate settings, including the source-mapped display, input,
audio and USB drivers in the runtime inventory. It is a host-side audit aid, not a systemd
compatibility test or a substitute for hardware evidence.

== Hardware evidence and next gates

The link:hardware-inventory.adoc#runtime-baseline[owner-reported runtime baseline]
records the sanitized findings. Internal partition mappings confirm eMMC, with
boot (`mmcblk0p28`) and recovery (`mmcblk0p2`) each measuring 33554432 bytes.
The supplied configuration matches the reference build's recorded hash. The later
private installed-boot copy matches the documented CI candidate, while exact
binary-to-source reproducibility remains unverified. A mounted cgroup2 hierarchy,
`mtkfb` framebuffer and input-device enumeration provide concrete starting points
for the next compatibility and driver checks.

The installed Ubuntu Touch systemd tools and subsequently queried active system
manager report `255.4-1ubuntu8.17`. At the
observed cgroup v2 root, `memory` is the only advertised controller and is enabled
for children; the other `/proc/cgroups` entries do not establish v2 availability.
See the link:hardware-inventory.adoc#runtime-cgroups[cgroup evidence] before
designing resource-control or delegation assumptions. Compatibility with pinned
systemd 261 remains unresolved.

Private preservation has started over the Mac's normal-mode USB connection. The
link:recovery-preparation.adoc[recovery preparation record] identifies inspected
Ubuntu Touch CI candidates, their hashes, stock-firmware research limits and
read-only preparation using the owner's Mac. Private boot/recovery/dtbo copies
are verified by exact sizes, saved-file hashes and independent phone hashes.
Installed boot exactly matches the documented CI candidate; installed recovery

=== Follow-up: temporary boot trial and USB probe
