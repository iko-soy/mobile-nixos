= First I2C bus trial

Status on 2026-10-16: *run once with the owner's explicit approval. The
controller probed in the kexec'd kernel, but the pin gate read the bus pins'
mode as 9 rather than 1, so the scan was skipped as the procedure requires;
mode 9 turned out to be function 1 as MediaTek reads it. See
<<result,the result>>.* Each repetition needs the owner's explicit approval
of this exact procedure.

The link:native-diag-trial.adoc[diagnostic trial] found no I2C controller
enabled in the native kernel's tree, and the
link:native-dtb-kexec-trial.adoc[tree-replacing kexec trial] showed that a
kexec'd kernel can be given a modified tree. This trial makes the first real
change that way: from the first boot it kexecs into the same kernel with the
bootloader's tree plus one property, the status of the I2C controller at
`0x11011000`, which carries only passive sensors. In the next kernel it checks
that the controller probes and that the bus's pins are in I2C mode, then scans
that bus once with reads only, to see which of the sensors answer. No device
node is added, so no device driver binds and nothing is written to any
device. The original recovery is then
restored. Ubuntu Touch's boot and `dtbo` partitions are never written, and
Linux never sees the phone's storage.

The owner approved the procedure and ran the partition reads, the entries, the
Volume Up start and the unlocks; watchers ran the fastboot steps, the push and

* *Preconditions and Part 1.* As before: battery full and charging, no update,
  empty recovery command directories, boot, recovery and dtbo identical to
  their preserved copies and no control region changed since the latest copy;
  `Writing 'recovery' OKAY`, and step 7 read recovery back as `07070c4d...`.
* *Question 1, yes.* SSH answered by 59 seconds of uptime and `titan-session
  end-in 40` moved the end to 2459 seconds. All eight CPUs came up, the core
  power-down driver registered, NixOS ran at 34 °C, no I2C adapter existed and
  `/soc/i2c@11011000` read `disabled`.
* *Question 2, yes.* The copy of the bootloader's tree matched its record;
  after `fdtput` the two trees' sources differed in that node's `status` line
  only. `kexec_load` from the bootloader's own tree, its first run, returned
  0 with the kernel at `0x42400000`, over the running kernel's data, which is
  normal for `kexec_load`, and the initrd, tree and purgatory just above; the
  placement check passed. After `systemctl kexec` the device was back 20
  seconds after leaving. The next kernel brought up all eight CPUs with the
  first boot's reserved memory, its tree read `okay` for the node and
  differed from the one handed over only in `/chosen`, and exactly one
  adapter existed: `i2c-1`, the controller at `11011000`, with `/dev/i2c-1`.
  The driver probed without error (`no pinctrl handle`, at debug level).
* *Question 3, not answered.* The pin modes were read from
  `/sys/kernel/debug/pinctrl/10005000.pinctrl-pinctrl_paris/pins`, the path
  this kernel uses rather than the procedure's `10005000.pinctrl`. GPIO81 and
  GPIO84 read mode 9, not 1; GPIO87 and GPIO88 read 9, and GPIO163 and
  GPIO164 read 10. The bus lines read high with their pull-ups on. As the
  procedure requires, the scan was skipped: no I2C transfer ran, and the
  controller's interrupt count stayed 0.
* *Question 4, yes.* `titan-session end-in 1` at 188 seconds of uptime; the
  device left 89 seconds later and Ubuntu Touch booted (`bootreason=reboot`).
  From Ubuntu Touch, `sudo /sbin/reboot bootloader` reached fastboot, the
  preserved original was written (`Writing 'recovery' OKAY`) and Ubuntu Touch
  returned. The read-back found recovery `4dd1c1f7...`, with boot and dtbo
  unchanged throughout; of the control regions only `expdb` changed, as after
  every boot. The Part 4 sensor check was not done: this Ubuntu Touch offers
  no automatic brightness, and with no transfer having run there was nothing
  for it to catch.

Afterwards, read-only: Ubuntu Touch's own GPIO table
(`/sys/devices/platform/1000b000.pinctrl/mt_gpio`) reports mode 1 for GPIO81,
GPIO84, GPIO87 and GPIO88, mode 2 for GPIO163 and GPIO164, and mode 1 for
GPIO48 and GPIO49, the pins of the charger bus its kernel uses. Both kernels
read the same 4-bit mode field, but MediaTek's MT6771 pin driver sets
`nfuncs = 8` and prints a mode of 8 or more as that value minus 8
(`pinctrl-mt6771.c`, `pinctrl-paris.c`), while mainline's MT8183 data sets no
`nfuncs` and prints the raw value. The register holds 9, set by the
bootloader, in both systems, and MediaTek reads it as function 1: the bus
pins were in their `SDA1` and `SCL1` function, as under Ubuntu Touch, and the
gate was too literal. A repeat needs the gate to compare the mode modulo 8
and the corrected debugfs path.

The session data and kernel logs are in the private evidence directory. This
shows the native kernel driving an I2C controller from a tree handed over by
kexec, and the first `kexec_load` with the bootloader's own tree. It does not
show which sensors answer.

== Basis

* *Kernel.* The kernel of the earlier trials, unchanged: `Image.gz`
  `69f24259affbdd7fbee6a897d8d6b85fd4a1beaa2c6e09ff2bf5b655b3e2c548`; the
  uncompressed kernel for kexec
  `ce4510e02bcd75dbc798504a4460406484eb47b239c6271b29b0ba628c09ca5c`. Its
  configuration has the controller's driver (`CONFIG_I2C_MT65XX`) and the
  character device for userspace (`CONFIG_I2C_CHARDEV`) built in. The
  controller's node has its clocks, interrupt and DMA channel and no
  `clock-frequency`, so the driver runs the bus at 100 kHz.
* *Pins.* The tree sets no pin function for the bus, and the controller's
  driver touches no pin mux. Bus 1's signals are `SDA1` on GPIO81 and `SCL1`
  on GPIO84 in mode 1, with alternatives on GPIO87 and GPIO88 and on GPIO163
  and GPIO164 in mode 3. Ubuntu Touch's kernel is a sensor-hub build, in
  which MediaTek's sensor co-processor (SCP) drives these sensors through its
  own I2C controllers, so its working sensors are no evidence that the main
  CPU's controller reaches them. The session therefore reads the pins' modes
  before the scan.
* *Expected answers.* If the pins are in I2C mode and the sensors powered,
  most likely the magnetometer at `0x0c` and the light and proximity sensor
  at `0x51`: their supply is always on, while the overlay may name parts
  that are not fitted, and an accelerometer that no bus lists may answer.
* *Stage 0 and store.* The previous configuration with `i2cdetect` alone,
  statically linked from i2c-tools, so that no I2C writer (`i2cset`,
  `i2cget`, `i2ctransfer`, `i2cdump`) is anywhere in the store:
  stage 0's ramdisk
  `f1a8a87f0de4362540425177dab42a9deff3c95d5d5daec02e6b00d3e6f4c222`, which
  pins the store squashfs, 112357376 bytes,
  `10e067e20d4ecd3f37b9640e23a65ba99cf03495c7d4ecf700c3aeff0c44ed22`; the
  kexec payload pairs the kernel above with this ramdisk.
* *Image.* 16513024 bytes, SHA-256
  `16dd05a5a0cfc0c0436f121a7d13967fb87f24799334225c4ad9e5a4ec31f3d7`; padded
  to 33554432 bytes,
  `07070c4d5bf2bd2bb7867ecdfd8313b20c67c57f2126eb107608fcb2fe54ec1d`
  (`tools/flash-recovery.py --profile ram-nixos-8`).
* *Checks.* All five VM cases pass, including that `i2cdetect` is present
  and no I2C writer is in the store, and the phone checks find none in the
  phone system's closure. `titan-dtb-check` now also compares the trees'
  reserve maps. An independent review of this procedure confirmed the bus
  mapping, the DMA channel, the interrupt and the clocks against the vendor's
  bus 1, and that the scan only reads; its findings are fixed.

== Procedure

*Part 1: write the image.* Steps 1 to 7 of the
link:repo-kernel-trial.adoc[repository-kernel trial], with `--profile
ram-nixos-8` and the image
`native-ram-image-v10/UNTESTED-UNSIGNED-native-ram.img`; step 7 must read
recovery back as `07070c4d...`, with boot and dtbo unchanged.

*Part 2: run the session.*

[start=8]
. *Listen:* start `tools/ram-nixos.py --wait 900` as its own job, with the
  private copy of the store squashfs, its pinned size and SHA-256, a new
  private output directory and the dedicated key; and a watcher that records
  every USB device change and whether Ubuntu Touch or fastboot appears after
  the image.
. *Start, owner-run:* keep the cable connected, power the phone off from
  Ubuntu Touch, hold Volume Up and press Power, and release both once the
  unlocked-state warning appears; allow the accessory if macOS asks. No
  confirmation is needed: the session starts when SSH answers.
. *Session:* at once and only once `titan-session end-in 40`; then the
  records of the tree-replacing kexec trial: the kernel log, CPUs, memory
  map, reserved memory, command line, the tree with its SHA-256 and reserve
  map, and the temperature; and that no I2C adapter exists. Read-only
  throughout: nothing written in sysfs, debugfs or configfs, no debugfs
  register dumps other than the pin modes of step 12, and no I2C command.
. *Kexec with the bus enabled:* with at least ten minutes left and the CPU
  below 55 °C.
** Copy the payload's `Image` and `initramfs.cpio.gz` into `/run/kexec`, and
   the running tree with `cp /sys/firmware/fdt /run/kexec/fdt-i2c.dtb`,
   which must match the saved record; set the status with `fdtput -t s
   /run/kexec/fdt-i2c.dtb /soc/i2c@11011000 status okay`, check with
   `fdtget` that it reads `okay`, and check that the trees' `dtc` sources
   differ only in that node's `status` line.
** Run `strace -f -e trace=kexec_load,kexec_file_load titan-kexec --dtb
   /run/kexec/fdt-i2c.dtb <its SHA-256> /run/kexec/Image <its SHA-256>
   /run/kexec/initramfs.cpio.gz <its SHA-256> titan_kexec=i2c`, which must
   show `kexec_load` and its segments, with `/sys/kernel/kexec_loaded`
   reading `1`.
** The placement check of the tree-replacing kexec trial: each segment
   within one `System RAM` range of `/proc/iomem` read after the load,
   overlapping none of its `reserved` ranges, the reserved-memory nodes'
   `reg` ranges or the tree's `/memreserve/` entries. If any check fails, go
   to the end step without starting the kernel.
** Then `systemctl kexec`, `tools/ram-nixos.py --wait 900` as its own job
   once the device has left, and the records, which must show eight CPUs,
   the first boot's reserved-memory lines and nodes,
   `/proc/device-tree/soc/i2c@11011000/status` reading `okay`, and a tree
   that differs from `fdt-i2c.dtb` only in `/chosen`.
. *Bus check, read-only:*
** `ls /sys/bus/i2c/devices` must show only `i2c-1`, and `readlink -f
   /sys/bus/i2c/devices/i2c-1` must end in `/11011000.i2c/i2c-1`; every
   adapter of this driver has the same name, so the name proves nothing.
** *Pin modes, reading debugfs:* save the lines for GPIO81, GPIO84, GPIO87,
   GPIO88, GPIO163 and GPIO164 from `/sys/kernel/debug/pinctrl/
   10005000.pinctrl/pins`, which only reads the pin controller's registers;
   the mode is the first digit after each pin's number. GPIO81 and GPIO84
   must read mode 1, and the other four must not read mode 3; otherwise skip
   the scan and go to the end step.
** *Scan:* save the `11011000.i2c` line of `/proc/interrupts`, run `time
   timeout 300 i2cdetect -y -r 1` once, which reads one byte from each
   address from `0x08` to `0x77` and writes nothing, then save the
   interrupt line and the kernel log again. No other I2C command. The
   driver logs a missing answer only at debug level, so the timing and the
   interrupt count tell the outcomes apart: a scan in seconds with
   interrupts counted is a real result; about 224 seconds with no
   interrupts means a clock line held low, pins not reached or no
   interrupt; more than eight answering addresses means a data line held
   low, and the table is no result.
. *End:* `titan-session end-in 1`; the session deadline must restart the
  phone into Ubuntu Touch within about two minutes. Only if it has not after
  three minutes, `titan-session end`.

*Part 3: restore.* From Ubuntu Touch, `sudo /sbin/reboot bootloader`
(owner-run); then, as in the earlier trials, write the preserved original
with the `original-recovery` profile, return, and read recovery back as
`4dd1c1f7...`, with boot and dtbo unchanged.

*Part 4: compare.* A normal-mode control-region copy after Part 3, compared
with the one from step 2 (`expdb` changes on every boot). Then, owner-run in
Ubuntu Touch, a check that the light and proximity sensor and the compass
still work: a read that timed out ends without a stop condition, and a
sensor left holding the bus would keep it on its always-on supply through a
restart. If they do not, a full power-off restores them; record either way.

== Residual risks

* The scan sends one read to every address on a bus with five sensors and
  writes nothing. Reads leave these parts' configuration unchanged, but a
  device could react to a read in an unexpected state; none of these types
  is known to.
* The bus's pins are set by the preloader, not by this tree. If they are not
  in I2C mode, the controller's transfers do not reach them: nothing
  answers, and nothing else is driven.
* The controller and its DMA channel run under the native kernel for the
  first time. The driver resets the controller when it probes and after
  every address that does not answer, and each transfer ends by switching
  off clocks that the bootloader left on, including the I2C source clock
  shared with the other controllers and the PWM block; nothing in Linux uses
  those, and the sensor co-processor is assumed to stay in reset, since only
  the vendor kernel releases it.
* The kexec runs `kexec_load` with the bootloader's own tree for the first
  time; its mechanics are those of the tree-replacing kexec trial's, which
  passed. Its old kernel's shutdown makes the core power-down driver's calls
  without a guard, as in the earlier kexecs.
* Charging buses stay disabled: the tree changes one controller's status,
  and the check refuses any change to reserved memory.

== What this can and cannot show

Success shows the native kernel driving an I2C controller in a tree handed
over by kexec, and which of the vendor's sensors answer, the start for adding
their drivers. It does not show any device driver, the other buses, the
touch panel, the keyboard or the display.
