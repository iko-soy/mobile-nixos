= I2C device identification trial

Status on 2026-10-17: *run once with the owner's explicit approval; both
devices answered the identification reads with zeros, which identifies
neither. See <<result,the result>>.* Each repetition needs the owner's
explicit approval of this exact procedure.

The link:native-i2c-scan-trial.adoc[I2C bus scan trial] found two devices
answering on the sensors' I2C bus at `0x11011000`, at `0x2c` and `0x60`, and
none at the addresses of the vendor overlay, whose list is a reference
board's. This trial repeats that trial and then reads one identification
register from each device with `titan-i2c-id`, a tool that can make exactly
two reads: register `0x00` of `0x2c`, one byte, and
register `0x0c` of `0x60`, two bytes. Each read is one combined transfer that
writes the register's address and then reads. Everything else is unchanged.

== Result (2026-10-17)

The owner ran the step 2 copies, approved the procedure, and ran the entries,
the Volume Up start and the unlocks; watchers ran the fastboot steps, the push
and the USB log, and the session ran over SSH from the Mac.

* *Preconditions and Part 1.* The baseline found the battery full and
  charging, no update pending and empty recovery command directories; the
  step 2 copies found boot, recovery and dtbo identical to their preserved
  copies and no control region changed since the scan trial's Part 4 copy.
  `Writing 'recovery' OKAY`, and step 7 read recovery back as `7bca74ec...`.
* *Question 1, yes.* As in the scan trial: the tree copy differed from the
  running tree in the node's `status` line only, `kexec_load` placed the
  kernel at `0x42400000` and the rest just above, and the placement check
  passed. The next kernel brought up all eight CPUs with the first boot's
  reserved memory, a tree that read `okay` for the node and differed from the
  one handed over only in `/chosen`, and exactly one adapter, `i2c-1`, the
  controller at `11011000`, with `/dev/i2c-1` device 89:1. GPIO81 and GPIO84
  read function 1 and high, with pull-ups on. The scan again found exactly
  `0x2c` and `0x60`, in 0.11 seconds, while the interrupt count rose from 0
  to 222, with no I2C error logged and both lines high afterwards; the gate
  for the identification reads passed.
* *Question 2: both answered, with zeros.* `titan-i2c-id` exited 0 and
  printed `00` for register `0x00` of `0x2c` and `00 00` for register `0x0c`
  of `0x60`. The interrupt count rose by exactly 2, one per transfer, and the
  kernel logged nothing: both devices acknowledged their address and the
  register byte. Neither returned the value expected, neither the `qmc6308`
  family's `0x80` nor the `vcnl4000` family's low byte `0x86`.
* *Question 3, yes.* GPIO81 and GPIO84 again read high after the reads.
* *Question 4, yes.* `titan-session end-in 1` at 154 seconds of uptime; the
  phone restarted about 80 seconds later and Ubuntu Touch booted
  (`bootreason=reboot`). From Ubuntu Touch, `sudo /sbin/reboot bootloader`
  reached fastboot, the preserved original was written (`Writing 'recovery'
  OKAY`) and Ubuntu Touch returned. The read-back found recovery
  `4dd1c1f7...`, with boot and dtbo unchanged throughout; of the control
  regions only `expdb` changed, as after every boot.

The zeros do not identify the devices, for two reasons:

* *Other parts read zero there.* At `0x60`, Vishay's VCNL4035 keeps its
  white-light data at `0x0c` and its identification register at `0x0e`,
  which reads `0x80` (mainline `vcnl4035.c`); light data reads zero while the
  sensor is shut down, as it is from power-on. At `0x2c`, QST's older
  magnetometers such as the QMC6983 keep axis data at `0x00`, which reads
  zero before a measurement (from memory, unverified).
* *A read that delivered nothing would look the same.* i2c-mt65xx moves all
  data through the controller's DMA channel, and i2c-dev hands the driver a
  copy of the caller's buffer, which `titan-i2c-id` fills with zeros. A
  receive path that delivered nothing would therefore print the same zeros.
  Neither the scan, which discards the byte it reads, nor this run tests that
  path.

A repeat that fills the buffer with a value such as `0xa5` before each read
would settle the second point, and reads of the other parts' identification
registers the first; each is its own trial. The session data and kernel logs
are in the private evidence directory.

== Basis

* *The tool.* `ram-nixos/i2c-id.c`, built statically. It refuses unless
  `/sys/bus/i2c/devices/i2c-1` resolves to the controller at `11011000` and
  the adapter supports plain I2C transfers; then, for each entry of its
  fixed table, it sends one `I2C_RDWR` transfer of two messages: a write of
  the one-byte register address and a read of one or two bytes. It checks
  that `/dev/i2c-1` is the I2C device 89:1, stops at any error but a missing
  answer, and exits 0 when both reads succeed, 1 when one failed and 2 when
  it refused. It takes no arguments and has no other code path that writes.
  The VM case and the phone checks, which run the phone's own binary,
  confirm that it refuses where no such adapter exists.
* *On the bus.* i2c-mt65xx sends each transfer as one combined write-read:
  start, the address with write, the register byte, a repeated start, the
  address with read, the data, stop; there is no stop between, so no SMBus
  command made of a single byte completes. Both transfers are byte for byte
  the first identification reads of mainline's `qmc6308` and `vcnl4000`
  drivers, and neither register clears anything when read on those parts.
  This is the first combined write-read, and the first transmit through the
  controller's DMA channel, on this controller; the scan only read.
* *Image.* As in the scan trial, with `titan-i2c-id` added: stage 0's
  ramdisk `97be934c2eb5a1fbe33863712fe065cd2e1b2f77899ed083e853b33fab57e3b7`,
  which pins the store squashfs, 112373760 bytes,
  `bb9f518dfbf0e721b6a733d4a8eb5390db89fa3de6766d38327a76c72e6e5162`; the
  kexec payload pairs the unchanged kernel with this ramdisk. The image is
  16513024 bytes, SHA-256
  `a4b76fcfb55e6b25eb14ceba5da39c8d00f74002440bb1f9645a1a6fb04ec8d5`; padded
  to 33554432 bytes,
  `7bca74ec3a4348744487060fea451062648e5d3fe815a3864dc9da96d8481dab`
  (`tools/flash-recovery.py --profile ram-nixos-9`).
* *Everything else.* The kernel, the tree change, the checks and the bus map
  of the link:native-i2c-scan-trial.adoc[I2C bus scan trial].

== Residual risks

As in the scan trial, and this time two devices also receive a one-byte
write, the address of the register to be read, followed by a repeated start
rather than a stop. For register-based parts such as the expected ones, that
only sets the read pointer. Among other parts that answer at `0x2c` or `0x60`
none is known to have a reset, one-time-programmable or power command at
register `0x00` or `0x0c`; a part of another kind could still treat the byte
differently, which the identification is meant to settle before any driver
is tried. A full power-off after Part 3 resets every device on the bus and
costs one start.

== What this can and cannot show

Success names the two devices on the native kernel's first working I2C bus,
which decides the drivers to try next. It does not show a driver, the other
buses, the touch panel, the keyboard or the display.
