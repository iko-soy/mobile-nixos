= Native-route diagnostic trial

Status on 2026-10-16: *run once with the owner's explicit approval; all three
questions were answered yes. See <<result,the result>>.* Each repetition needs
the owner's explicit approval of this exact procedure.

The link:native-boot-trial.adoc[first native-route boot] showed that the modern
kernel starts on the Titan, guards the eMMC and brings up USB device mode, but
the probe reports only five status lines, and with no display driver or serial
console the kernel's own log stays on the phone. This trial starts the same
kernel, device tree and overlay once more from the recovery partition with the
link:diag/README.adoc[diagnostic ramdisk], which sends the kernel log and a
fixed set of kernel and firmware state to the Mac, then restores the original
recovery. Ubuntu Touch's boot and `dtbo` partitions are never written, and the
image reads nothing from storage.

[[result]]
== Result (2026-10-16)

The owner approved the procedure and ran the partition reads, the entries, the
Volume Up start and the unlocks; watchers ran the fastboot steps and the
receiver.

* *Preconditions.* The baseline found the battery full and charging, no update
  pending or running and empty recovery command directories. Step 2 found
  boot, recovery and dtbo identical to their preserved copies, and no control
  region changed since the latest copy.
* *Part 1.* `fastboot flash recovery` reported `Writing 'recovery' OKAY`, and
  step 7 read recovery back as `5a55f9d7...`, with boot and dtbo unchanged.
* *Question 1, yes.* After the Volume Up start the boot ROM and preloader
  devices passed through, and 21 seconds after the boot ROM the image's USB
  device appeared. At 40 seconds of uptime the eight sections followed:
  610309 bytes, verified by count, hash and readback, with no section missing,
  truncated or unreadable.
* *Question 2, yes.* The image's device disappeared five seconds after the
  acknowledgement, the preloader passed through and Ubuntu Touch booted
  (`bootreason=reboot`). Its ADB interface appeared only once the owner had
  unlocked the screen, as after every boot.
* *Question 3, yes.* From Ubuntu Touch, `sudo /sbin/reboot bootloader` reached
  fastboot, the preserved original was written (`Writing 'recovery' OKAY`) and
  Ubuntu Touch returned. Step 13 read recovery back as `4dd1c1f7...`, with boot
  and dtbo unchanged throughout; of the control regions only `expdb` changed,
  as after every boot.

=== What the sections show

The sections are in the private evidence directory; identifiers are withheld
here.

* *Bootloader.* On a recovery start it applied the image's own overlay from
  the recovery-DTBO section: both of its nodes are in the passed tree and none
  of the 92 node names of the stock `dtbo` overlay. It added its usual
  `/chosen` boot tags and initrd location, all fourteen reserved-memory
  regions in the tree's empty `/reserved-memory` node (eleven `mblock-*`
  regions for DRAM calibration, the log store, ATF and its log, SSPM, TEE,
  the RAM console, pstore, `minirdump` and the framebuffer at `0x7e340000`,
  plus a movable CMA zone and two DRAM dummy-read areas), and a command line
  that starts with the tree's `bootargs` and keeps every argument of the
  image's own.
* *Kernel log.* 5926 records from the first one, so the 2 MiB buffer was in
  effect; the producer read them at 41 seconds of uptime. All eight CPUs (four
  Cortex-A53, four Cortex-A73) came up through PSCI 1.0, and 5.66 GiB of the
  6 GiB were available. Unused clocks, power domains and regulators were all
  left on. The only deferred probe still pending was the SVS block, which
  needs the CPU frequency tables this tree omits.
* *Drivers.* 60 of 81 platform devices found drivers: the clock controllers
  (through the MT8183 drivers), pin control, power domains, the watchdog, the
  PMIC wrapper and the MT6358 with its regulators and audio codec, the thermal
  sensor, the eMMC (high speed; 38 partitions, both boot areas, RPMB as a
  character device), the USB device controller (high speed), the Mali-G72
  under panfrost, the display blocks and MIPI D-PHY, the audio front end and
  the efuse.
* *Not yet working, as expected.* The display pipeline creates no output
  because DSI0 and DPI0 are absent from the tree. No I2C controller is
  enabled, so the keyboard, touchscreen, sensors and MT6370 are unreachable.
  The CPU interconnect frequency driver has no regulator, and the MT6358 RTC
  and AUXADC have no driver bound.
* *Regulators.* The regulator driver logged one voltage change: `vxo22` from
  the bootloader's 2.24 V to 2.2 V, the value the vendor kernel also sets in
  Ubuntu Touch.
* *Warnings to address.* "Kernel image misaligned at boot": the bootloader
  loads the kernel at `0x40080000`, and arm64 kernels now expect a 2 MiB
  aligned address. A known upstream warning about the `mtu3` trace events and
  a T-PHY device-link message appear at boot; USB works regardless. The random
  number generator finished initializing only at 37 seconds, since no hardware
  RNG driver runs.

This is the modern kernel's own view of the Titan, and it sets the next steps:
DSI0 with the NT35595 command-mode panel for the display, the I2C controllers
for the keyboard, touchscreen and MT6370, the RTC, a 2 MiB aligned kernel load
address, and possibly a RAM log on the bootloader's pstore region so that a
later crash can be read back after a restart.

== Questions

. Does the diagnostic image start like the first native image, and does the
  verified transfer of its sections reach the Mac?
. Does the phone restart by itself after the transfer and boot Ubuntu Touch?
. Does the restore work as before, from fastboot entered from Ubuntu Touch?

The sections then answer what the first boot could not show:

* the complete kernel log of the boot, with the memory layout, every driver
  that probed or failed, and the deferred probes still pending at about ten
  seconds (`log_buf_len=2M` keeps the earliest records);
* which overlay the bootloader applied on a recovery start, which reserved
  memory and command line it added, and its other fixups, from the device tree
  as it was passed (`/sys/firmware/fdt`; the kernel blanks only its KASLR and
  RNG seeds);
* which devices found a driver, with the kernel log naming the deferred probes
  still pending and why;
* the interrupts in use, the processors online, the partitions the kernel
  enumerated and the physical memory map.

== Basis

* *Kernel, device tree and overlay.* Unchanged from the first native boot:
  `Image.gz` SHA-256 `461372e7dd4f98f1924ae9ecae0381731d75cd0cf92f5b6f3b30eddce59986d1`
  and the same DTB and recovery-DTBO tables.
* *Ramdisk.* `usbDiag.ramdisk`: PID 1 is the probe built for the modern kernel
  with the control pipeline of the offline acquisition image, which ran on
  the vendor kernel with the same gadget and the same TTR1 sender; only the
  producer is new. It guards the complete eMMC set read-only, binds the fixed
  ACM gadget, waits until 40 seconds of uptime, then sends eight sections
  under the label `titan-diagnostics` with an 8 MiB cap: the command line,
  `/dev/kmsg`, `/sys/firmware/fdt`, a device-driver binding table from
  `/sys/bus`, `/proc/interrupts`, `/proc/cpuinfo`, `/proc/partitions` and
  `/proc/iomem`. A section it cannot read is reported as missing or as an
  error and the rest still follow. PID 1 restarts the phone five seconds after
  the Mac acknowledges the transfer, within about 35 seconds after a failure,
  and at the latest at its 300-second deadline. Ramdisk 1960531 bytes,
  SHA-256 `9ae8c3dd6d0c824305445449e7c866fefc046d4fdcdab5d8fb71a866b7942eac`.
* *Image.* As before, with the diagnostic ramdisk and `log_buf_len=2M` added
  to the command line: 17606656 bytes, SHA-256 `8a58da6ccf326fb6c8432e18a9d5c57b2a9c4b3bfcf44909a93df4c01f029bde`; padded
  to 33554432 bytes, `5a55f9d7a54c9f5bb757b32955f2488909457a042ba42509182fcacb7ec7c6ee` (`tools/flash-recovery.py --profile
  native-diag`).
* *Checks.* A TCG guest runs the VM build of the same code against a blank
  virtio disk, receives and splits the sections with the real receiver and
  splitter, and checks them against the guest; the guest then restarts by
  itself before its deadline, with the disk unchanged. The phone binaries are
  checked for the modern names and for no VM or vendor-kernel names, and
  refuse to run outside the offline environment. An independent review
  checked the change against the Linux 7.3-rc3 source; its findings are fixed
  (see the residual risks). The other ramdisks and the first native image are
  byte-identical to before.

The sections contain device identifiers: the serial number is on the command
line and in the device tree's `/chosen` node. They are saved only in the
private evidence directory; repository records describe findings, not raw
data.

== Preconditions

As in the link:native-boot-trial.adoc[first native-route boot]: the owner
present, a direct cable, battery at least 60%, no update pending, no recovery
command file, both private copies of the original recovery (`4dd1c1f7...`)
verified, and a normal-mode control-region copy right before the trial with
`para` matching the latest copies. From step 5 until step 13 passes: no system
update, factory reset, `reboot recovery` or Volume Up start other than step 9
and the rows below.

== Procedure

*Part 1: write the image.* Steps 1 to 7 of the
link:repo-kernel-trial.adoc[repository-kernel trial], with `--profile
native-diag` and the image
`native-diag-image-v3/UNTESTED-UNSIGNED-native-diag.img`; step 7
must read recovery back as `5a55f9d7...`, with boot and dtbo unchanged.

*Part 2: run the diagnostic image.*

[start=8]
. *Listen:* start `tools/receive-diagnostics.py --output <new private
  directory>`, and a watcher script (not part of the repository, as in the
  earlier trials) that polls `adb -d get-state` and `fastboot devices` and
  records which appears next, for up to 15 minutes.
. *Start, owner-run:* keep the cable connected, power the phone off from
  Ubuntu Touch, hold Volume Up and press Power, and release both once the
  unlocked-state warning appears.
. *Expected:* the screen may keep the bootloader's last picture or go dark.
  Within about 40 seconds the image's USB device appears and the receiver
  starts; once the kernel has been up for 40 seconds the sections follow, well
  under 8 MiB, and the receiver prints them with their sizes after verifying
  count, hash and readback. About five seconds later the phone restarts and
  boots Ubuntu Touch.

*Part 3: restore.* From Ubuntu Touch, `sudo /sbin/reboot bootloader`
(owner-run); then, as in the earlier trials, write the preserved original
with the `original-recovery` profile, return, and read recovery back as
`4dd1c1f7...`, with boot and dtbo unchanged.

*Part 4: compare.* A normal-mode control-region copy after Part 3, compared
with the one from step 2 (`expdb` changes on every boot).

== Residual risks

* This is the second run of the modern kernel on this phone, now for about a
  minute instead of 150 seconds, so the first boot's residual risks remain: an
  early hang has no feedback channel and no way out but the battery running down;
  the MT6358 regulator driver binds with mainline constraints; the eMMC driver
  is not the vendor's; no charger driver runs. The first boot showed none of
  these problems.
* `log_buf_len=2M` makes the kernel allocate about 9 MiB early in boot: the
  2 MiB text buffer and its record descriptors. If that allocation failed, the
  kernel would keep its built-in buffer and say so in the log.
* The producer only reads the files listed above and the `/sys/bus` directory
  listings and driver links; it opens no block device and writes nothing on
  the phone. It reads no device attribute: the independent review found that
  `waiting_for_supplier` takes the device lock and can deadlock against a
  driver probe in progress, which would also have blocked the restart, so that
  column was removed. Reading `/sys/firmware/fdt` copies the tree the kernel
  already holds.
* The pipeline, gadget and sender have run on the vendor kernel, and the
  modern kernel's ACM gadget has carried the probe's status lines to the Mac,
  but a TTR1 transfer, which also sends from the Mac to the phone, has not yet
  run on the modern kernel.

== What this can and cannot show

Success gives the modern kernel's own view of the Titan: its log, the device
tree the bootloader really passed, and which hardware found drivers. It is the
basis for the next device-tree and driver changes, such as the display panel,
and for deciding between them. It changes nothing on the phone beyond the
recovery partition, which the procedure restores, and it does not show
display, input, charging, audio, radios or a NixOS userspace.
