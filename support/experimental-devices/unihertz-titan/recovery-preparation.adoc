== Read-only preparation on the Mac

. Obtain link:https://developer.android.com/tools/releases/platform-tools[Google SDK Platform-Tools for Mac]
  if needed, and record the installed versions. Use a USB data cable and leave
  the phone in its current Ubuntu Touch session.
. Check ordinary USB/ADB connectivity and the shell's read permissions. From the
  extracted `platform-tools` directory:
+
[source,sh]
----
./adb version
./fastboot --version
./adb -d get-state
./adb -d shell 'id -u; uname -r'
./adb -d shell 'for label in boot recovery dtbo; do
  printf "%s: " "$label"
  if [ -r "/dev/disk/by-partlabel/$label" ]; then
    printf "readable\n"
  else
    printf "not readable\n"
  fi
done'
----
+
These commands do not switch device mode or write partitions. `adb -d` selects
a USB device and fails if multiple USB devices are present. ADB can start its
host-side server; authorize only the intended Mac if the phone requests it.
Keep transport identifiers private. Preserve errors if ADB or a label is
unavailable; do not enable root, change permissions or reboot to work around them.

. Before copying a partition, independently resolve its label and confirm its
  block-device type and size against the inventory. Boot is currently
  `mmcblk0p28` (33554432 bytes), recovery `mmcblk0p2` (33554432 bytes), and dtbo
  `mmcblk0p30` (8388608 bytes). Treat these as observed values to check, not
  universal Titan constants.
. Prepare bounded, read-only acquisition to a private directory on the Mac
  outside Git (directory `0700`, files `0600`). If the current shell cannot read
  a partition, first determine the existing supported privilege mechanism;
  do not blindly alter phone security settings. Hash each completed copy, verify
  its byte count and inspect it with the repository's existing tools. Compare
  the installed boot/recovery hashes to the candidates above.
. Plan userdata and device-specific calibration/radio preservation separately.
  Boot/recovery/dtbo copies alone do not preserve the operating-system data or
  NVRAM/NVDATA. Several relevant partitions are mounted read-write; raw live
  copies are not automatically filesystem-consistent backups.
. Record actual recovery entry, host recognition and restoration only after the
  owner explicitly authorizes the necessary mode changes or writes. A matching
  image hash and an installed host tool are not a demonstrated restore.

=== Bounded partition-table preservation

A fresh private acquisition completed on 2026-10-14 using the explicit zero-disk-GUID

`tools/acquire-gpt.py` preserves two fixed 32768-byte regions at the beginning
and end of the measured 125074145280-byte eMMC user area through normal-mode
ADB. Together they occupy 64 KiB. Fresh kernel metadata must show that neither
region intersects a partition before each content read. The helper revalidates
the MMC type, non-removable parent, block-node identity, capacity, 512-byte
sector geometry and known boot/recovery/dtbo/userdata mappings. It accepts no
alternative disk path, capture size or offset.

The host validator implements bounded structural checks from the
link:https://uefi.org/specs/UEFI/2.11/05_GUID_Partition_Table_Format.html[UEFI GPT format].
It requires a protective MBR, valid primary and backup GPT
headers and entry-array CRCs, reciprocal header locations, matching table
contents, bounded non-overlapping partition ranges and unambiguous partition
identities. Every used entry must agree with the complete kernel partition map.
Both copies must fit inside the two fixed captures; an unsupported layout stops
the helper instead of expanding the read. CRC agreement detects corruption;
it is not cryptographic authentication.

The installed table has a zero disk GUID in both headers. Offline inspection
confirmed matching valid header/array CRCs and byte-identical arrays. All 38 used
entries have numbers, names and ranges agreeing with the kernel map; their
partition GUIDs are distinct and nonzero. The fixed Titan acquisition
profile therefore explicitly permits the zero *disk* GUID and records
`zero-disk-guid` as a warning. This value cannot identify the disk uniquely.
All other checks, including partition GUID validation and equality between
copies, remain required. The host inspector rejects zero disk GUIDs by default;
its separate `--allow-zero-disk-guid` option makes this exception explicit.
Neither program rewrites or normalizes any captured byte. Acceptance under this
policy is not a claim of strict UEFI conformance or a demonstrated restore.

The helper independently rereads both regions, compares their hashes with the
saved files and checks the partition map again before recording completion.
Matching observations show identical captured bytes and partition maps at the
sampled checks; they cannot exclude intervening changes or establish an atomic
snapshot of the entire device. These regions can contain GUIDs, device
identifiers or reserved vendor data. Keep all captures, parsed tables, manifests
and diagnostics private and outside Git, with directory mode `0700` and file
mode `0600`. Only reviewed geometry belongs in public findings.

  --sudo --output /absolute/private/new-gpt-backup
----

==== Sparse userdata backup feasibility

A follow-up rechecked `df`: 8262604 KiB used, 106356912 KiB available on userdata.
The phone already has e2image 1.47.0 and Zstandard 1.5.5. No phone software was
installed. The Mac has e2fsprogs and Zstandard, and a same-size synthetic sparse
file (119878418432 logical bytes) occupied only 32768 bytes on its local
filesystem. This checks hole support, not the backup size of actual phone data.

The link:https://github.com/tytso/e2fsprogs/blob/v1.47.0/misc/e2image.8.in[matching e2image manual]
documents `-r -a` for copying filesystem metadata and file data while omitting
unused blocks. The `-a` is essential: the default image contains metadata only.
This is a filesystem backup, not a byte-for-byte or forensic partition copy;
partition geometry and any data outside the filesystem need separate accounting.
Do not replace the exact boot/recovery/dtbo backups with this method.

Raw output can stream to stdout; QCOW2 creation requires a seekable output and
cannot use this pipe. The
link:https://github.com/tytso/e2fsprogs/blob/v1.47.0/misc/e2image.c#L658[raw stdout implementation]
emits zero bytes for skipped blocks, so compress on the phone before transport.
Save the compressed stream privately on the Mac, then decompress with sparse
output support when inspecting a working copy. This avoids a fully allocated
120 GB temporary file and avoids staging a backup on the phone's source
filesystem. Transferring a sparse file without preserving holes can expand it.

An entirely local 256 MiB ext4 fixture exercised `e2image -ra SOURCE -`, streamed
Zstandard compression, and `zstd -d --sparse` into a new ordinary image file.
The compressed output was 1064951 bytes; the restored image retained its
268435456-byte logical size while allocating 27148288 bytes. A read-only
`e2fsck -fn` passed. Extracted payload bytes matched, mode `0640` survived,
two hardlinks retained one inode, and the symlink survived. These synthetic
numbers are not a phone-backup size estimate or a Titan restore test.

With about 7.9 GiB currently used, a sparse/compressed filesystem backup is
plausible. A later check found approximately 58 GiB free on the Mac after saving
the two OS image files, so the earlier free-space figures are only snapshots.
Measure metadata/allocated blocks and enforce output/free-space limits before
acquisition; budget for both the archive and any sparse verification copy. Do
not promise an exact final size from `df` alone.

The remaining gate is consistency. `e2image` normally refuses a source mounted
read-write; `-f` would bypass that protection and must not be used for this
preservation plan. Userdata is still mounted writable, so no actual userdata
image was acquired. A separately approved quiescent/read-only environment is
needed before running the proposed pipeline. Sparse allocation solves the host
space problem without solving concurrent filesystem or calibration writes.

==== Host verification of an acquired sparse archive

`tools/verify-sparse-backup.py` checks an existing Zstandard-compressed raw ext4
archive on the Mac. It does not acquire data, contact the phone or establish
source quiescence. Record the source filesystem's exact logical byte count
separately from partition capacity; any partition tail needs separate accounting.
Preserve the acquisition commands, statuses and stderr with the archive. The
inspected e2image implementation can report a block read error and continue;
producer read errors must reject the acquisition even if it exits zero. A later
filesystem check cannot prove every original file-data block was read correctly.

The verifier requires explicit logical-size, allocation and free-space limits.
It tests sparse behavior on the destination with at most 32 MiB of temporary
scratch space, reserves another 4 MiB for bounded logs/manifests, and rejects a
destination that allocates the probe densely. It then presizes the output,
decodes with byte/time limits, skips zero blocks, checks physical allocation,
and compares decoded and saved-file SHA-256 hashes. Small images below 32 MiB
require a budget covering their full logical size: this Mac allocated some
small zero gaps densely despite supporting larger sparse files.

Only exact-size images with matching ext4 geometry, clean state and a successful
read-only `e2fsck -fn` become `filesystem.img`. Dirty, recovery-required, short,
oversized or failed images are rejected. The helper never mounts or repairs an
image; failures retain a private manifest and available diagnostics, while
removing its own partial image. An existing image or output directory is never
overwritten.

For an already acquired archive, set `FILESYSTEM_BYTES` from its independently
recorded geometry. This example allows 16 GiB for the verification image and
keeps an 8 GiB free-space reserve; choose limits using current free space and
the archive's measured allocation, not these illustrative values alone:

[source,sh]
----
python3 support/experimental-devices/unihertz-titan/tools/verify-sparse-backup.py \
  /absolute/private/userdata.ext4.zst \
  --expected-bytes "$FILESYSTEM_BYTES" \
  --max-allocated-bytes 17179869184 --min-free-bytes 8589934592 \
  --e2fsck /opt/homebrew/opt/e2fsprogs/sbin/e2fsck \
  --output /absolute/private/new-userdata-verification
----

A real local 32 MiB ext4/e2image fixture passed decoding, hash readback,
filesystem checking and file-content comparison, using under 8 MiB of physical
image allocation. A deliberately dirty clone was rejected without publication.
These checks exercise the host verifier; no Titan userdata archive or restore
was produced. The same integration can be repeated without accessing hardware:

[source,sh]
----
python3 support/experimental-devices/unihertz-titan/tools/tests/test_sparse_backup.py \
  --integration --output /absolute/private/new-synthetic-fixture
----

==== Consistency and retention requirements

A consistent full backup requires a separately authorized maintenance procedure:
stop all writers, including Android/modem services where relevant, and acquire
from an environment that leaves the targets unmounted. Inspect all relevant
mount namespaces, holders and raw writers. Do not silently freeze, unmount or
stop services during this read-only session. A filesystem-level export must
preserve metadata and be paired with an explicitly reviewed reconstruction plan;
copying home alone omits Nix, Android data and writable system state.

Retain a second verified copy on separate storage. Verify hashes again after
copying, and keep originals immutable during inspection. Linux ext4 can replay
its journal even with `ro`; use read-only block backing plus `ro,noload` when
examining a copy, and run any repair only on a disposable copy. See
link:https://docs.kernel.org/admin-guide/ext4.html[the ext4 documentation] and
link:https://docs.kernel.org/driver-api/mmc/mmc-dev-parts.html[eMMC boot partitions].

==== Pinned watchdog and ACM source audit

The pinned kernel archive was inspected on the Linux builder without executing
its contents. These are source-level constraints, not a rescue boot result.
The configured vendor watchdog does not use Linux `WATCHDOG_CORE`. Its
link:{kernel-src}/drivers/watchdog/mediatek/wdt/common/wdt_v2/mtk_wdt_v2.c#L1249[probe]
sets a 30-second timeout and normally enables the watchdog; the device-tree
`apwdt_en` property can override that default. The
link:{kernel-src}/drivers/watchdog/mediatek/wdk/wd_common_drv.c#L308[kernel kicker]
starts automatically with a 20-second interval and per-CPU `wdtk-*` threads.
The inspected path therefore does not require an Android userspace daemon just
to supply these kicks. Do not replace this with generic `/dev/watchdog`
assumptions or silently disable the watchdog.

The separate
link:{kernel-src}/drivers/misc/mediatek/aee/aed/monitor_hang.c#L1665[AEE hang detector]
starts with detection disabled; its `BOOT_UP_HANG` definition is commented out.
The normal countdown requires enabled detection and an Android `system_server`,
unless userspace explicitly sets its reboot flag. A standalone PID 1 should
not invoke those Android monitor ioctls. This audit does not establish all
kernel/firmware write paths, charging behavior or failure behavior. The retained
configuration has `CONFIG_PANIC_TIMEOUT=1`, and its `CONFIG_MTK_AEE_IPANIC=y`
exception handler registers panic and oops notifiers that request an immediate
watchdog reset before that timeout or a `panic=` override is consulted (source
analysis). The bootloader's handling of such an exception reset is unknown.

ACM can avoid an `adbd` dependency: the configured
link:{kernel-src}/drivers/usb/gadget/function/f_acm.c#L855[configfs ACM function]
allocates a kernel serial port. The active MTU3 phone implementation still needs
its link:{kernel-src}/drivers/usb/mtu3/mtu3_plat_v2.c#L454[regulator, clocks, PHY and extcon dependencies]
and link:{kernel-src}/drivers/usb/mtu3/mtu3_dr_v2.c#L403[USB role events].
Successful probe, gadget binding and Mac recognition without Android startup
remain untested. The serial driver initializes `tty_std_termios`, so a binary
transport must set raw termios on both ends and keep diagnostics separate.
Its link:{kernel-src}/drivers/usb/gadget/function/u_serial.c#L925[close path]
waits at most 15 seconds before discarding queued bytes: require explicit
length/hash framing and a host completion acknowledgement before closing.
The same driver logs the first three bytes of some TX/RX buffers through
`pr_notice`; acquisition logs must remain private. `CONFIG_U_SERIAL_CONSOLE`
is disabled in the retained configuration.

The pinned link:{kernel-src}/drivers/usb/gadget/function/u_serial.c#L1409[serial allocation]
registers `ttyGS` when the configfs ACM function is created, before UDC binding.
Its link:{kernel-src}/drivers/usb/gadget/function/u_serial.c#L783[open path]
permits opening without a connected USB peer, supporting raw setup before
binding. `O_NONBLOCK` does not bound every driver operation. Explicit unbind
requires a newline write to link:{kernel-src}/drivers/usb/gadget/configfs.c#L306[`UDC`];
then close all owned TTY descriptors before removing the function, whose
link:{kernel-src}/drivers/usb/gadget/function/u_serial.c#L1380[release path]
waits for old opens to close. Unbind aborts outstanding USB requests: the
link:{kernel-src}/drivers/usb/gadget/function/u_serial.c#L1023[reported TTY output queue]
does not establish host receipt of an already submitted request.

The separate link:usb/README.adoc[USB lifecycle fixture] exercises real
configfs ACM and host `cdc_acm` with a software `dummy_hcd` controller inside a
disposable Linux VM. It does not configure the phone, add USB to the production

An off-device link:transport/protocol.adoc[serial transfer prototype] now defines

The default `rescue.ramdisk` remains separate; the integrated build described

readiness before UDC binding;
bytes sent to a canonical/echoing TTY during startup cannot be recovered by

The package's public
https://gitlab.com/ubports/development/core/packaging/adbd/-/blob/05a118669fae0806703fc0ecbc7e43ab7cd8ebdb/debian/patches/0018-daemon-enable-reboot-command-on-non-Android.patch#L19[UBports reboot patch]
maps an ADB `reboot:<argument>` request to `/sbin/reboot <argument>`.
Its
https://gitlab.com/ubports/development/core/packaging/adbd/-/blob/05a118669fae0806703fc0ecbc7e43ab7cd8ebdb/debian/patches/adbd-unprivileged-user.patch#L53[unprivileged-daemon patch]

switches to the fixed `phablet` UID (32011) before shell execution, whether the
caller is `phablet` or root; it does not run the reboot command as root. The subsequent authorization and exact-version
systemd audit below narrows this path. The daemon source mapping alone does not
prove that a mode request will succeed or that its argument reaches the kernel
unchanged.

The pinned Titan kernel has a concrete consumer for the `bootloader` restart
argument. Its
link:{kernel-src}/drivers/watchdog/mediatek/wdk/wd_api.c#L657[`arch_reset` handler]
calls `rtc_mark_fast()` for that argument, then the vendor watchdog reset path.
The handler is registered with priority 128. The
link:{kernel-src}/drivers/misc/mediatek/rtc/mtk_rtc_common.c#L407[RTC setter]

===== Exact Ubuntu systemd source and live authorization boundary

The official source tag for `255.4-1ubuntu8.17` resolves to commit
`{systemd-rev}`. Its Debian patch archive matched the exact release `.dsc`
SHA-256, and every active quilt patch touching the inspected files was applied
to private working copies. The scheduled-shutdown patch changes an error path;
it does not move argument storage after authorization. This is an exact-version
source review, not a reproducible rebuild or signature verification of the
installed binaries.

When invoked through `/sbin/reboot`, systemctl selects its
link:{systemd-src}/src/systemctl/systemctl.c?id={systemd-rev}#n1087[compatibility parser].
That parser calls
link:{systemd-src}/src/systemctl/systemctl-compat-halt.c?id={systemd-rev}#n142[the reboot-parameter update]
before `halt_main` can consult logind. Every compatibility `reboot` invocation,
with or without an argument and including `-w`, creates, replaces or removes
`/run/systemd/reboot-param`: an argument is stored atomically and a missing
argument unlinks the file. A stored parameter that is not consumed by its own
reboot, for example after a privileged dry run, is applied by the next reboot of
any origin. Do not invoke reboot commands, including the dry-run form, as
read-only permission or connectivity probes.

Fresh normal-mode queries found the active manager at `255.4-1ubuntu8.17` and
logind running. For the queried ADB caller, `CanReboot` and `CanPowerOff` returned
`challenge`; the caller was not associated with a known logind session. That
result means authentication might permit the logind action, not that a request
has been authorized. It does not authorize the earlier client-side file write.
`CanRebootToBootLoaderMenu` returned `na`; that firmware-menu API is not a test
of Android fastboot or the generic `bootloader` reboot argument.

At the same inspection, `/run/systemd/reboot-param` was absent and its parent
was root-owned mode `0755`, with no effective write access for the ADB caller.
Systemctl was root-owned `0755`, without a file-capability attribute, and the
caller had no effective or ambient capabilities. Combining those observations
with the source predicts that an unprivileged named compatibility reboot fails
at parameter creation, before logind authorization. No reboot or dry-run
invocation was made to test this inference, and no permissions were changed.
The separate D-Bus
link:{systemd-src}/src/login/logind-dbus.c?id={systemd-rev}#n2714[`SetRebootParameter` setter]
has its own authorization and is not used by that compatibility parser. It was
not called.

The live PAM helper is setuid-root and matches the copy extracted from the
preserved Ubuntu image. The inspected `/etc/pam.d/adbd-pam-session` file serves
interactive sessions; commands and `reboot:` requests use the separate
`adbd-pam-session-noninteractive` service, whose file was not captured.
Privileged policy directories were not readable without elevation. The observed policy result applies to that caller and time; this is
not a complete audit of all authentication rules or future session contexts.

For an authorized ordinary reboot that reaches logind, the source follows the
reboot target and
link:{systemd-src}/units/systemd-reboot.service?id={systemd-rev}#n14[ordered shutdown units].
The live unit has `SuccessAction=reboot-force` after shutdown, unmount and final

The current probes found no `/run/nextroot`, `/run/initramfs/shutdown`, kernel

is `/sys/kernel/ccci/boot`; read it without writing the attribute. Its
link:{kernel-src}/drivers/misc/mediatek/eccci/ccci_core.c#L50[callback]
reports the link:{kernel-src}/drivers/misc/mediatek/include/mt-plat/mtk_ccci_common.h#L442[`MD_STATE` enumeration]:

6 reset and 7 waiting to stop. This is distinct from the internal FSM command
state: a newly allocated controller's reported state can still be 0.
Neither 0 nor 1 proves hardware power-off. Do not open CCCI monitor character

link:{kernel-src}/drivers/misc/mediatek/eccci/fsm/ccci_fsm_monitor.c#L43[close handler]
calls `force_md_stop`, even after a read-only open. Before calibration acquisition,
also verify absent userspace writers, unmounted targets and holders, preserved
partition identities, and stable pre/post acquisition hashes. Hash agreement
supports stability over the reads; it does not establish an atomic snapshot or
exclude firmware writes.
