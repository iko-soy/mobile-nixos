== Read-only preparation on the Mac

. Obtain link:https://developer.android.com/tools/releases/platform-tools[Google SDK Platform-Tools for Mac]
  if needed, and record the installed versions. Use a USB data cable and leave
  the phone in its current Ubuntu Touch session.
. Check ordinary USB/ADB connectivity and the shell's read permissions. From the
  extracted `platform-tools` directory:
+
[source,sh]
----
./adb version
./fastboot --version
./adb -d get-state
./adb -d shell 'id -u; uname -r'
./adb -d shell 'for label in boot recovery dtbo; do
  printf "%s: " "$label"
  if [ -r "/dev/disk/by-partlabel/$label" ]; then
    printf "readable\n"
  else
    printf "not readable\n"
  fi
done'
----
+
These commands do not switch device mode or write partitions. `adb -d` selects
a USB device and fails if multiple USB devices are present. ADB can start its
host-side server; authorize only the intended Mac if the phone requests it.
Keep transport identifiers private. Preserve errors if ADB or a label is
unavailable; do not enable root, change permissions or reboot to work around them.

. Before copying a partition, independently resolve its label and confirm its
  block-device type and size against the inventory. Boot is currently
  `mmcblk0p28` (33554432 bytes), recovery `mmcblk0p2` (33554432 bytes), and dtbo
  `mmcblk0p30` (8388608 bytes). Treat these as observed values to check, not
  universal Titan constants.
. Prepare bounded, read-only acquisition to a private directory on the Mac
  outside Git (directory `0700`, files `0600`). If the current shell cannot read
  a partition, first determine the existing supported privilege mechanism;
  do not blindly alter phone security settings. Hash each completed copy, verify
  its byte count and inspect it with the repository's existing tools. Compare
  the installed boot/recovery hashes to the candidates above.
. Plan userdata and device-specific calibration/radio preservation separately.
  Boot/recovery/dtbo copies alone do not preserve the operating-system data or
  NVRAM/NVDATA. Several relevant partitions are mounted read-write; raw live
  copies are not automatically filesystem-consistent backups.
. Record actual recovery entry, host recognition and restoration only after the
  owner explicitly authorizes the necessary mode changes or writes. A matching
  image hash and an installed host tool are not a demonstrated restore.

=== Bounded partition acquisition

`tools/acquire-partitions.py` is a read-only helper for this measured eMMC layout.
It accepts only boot, recovery and dtbo as a set, checks normal-mode ADB shell
transport support and revalidates partition identity, capacity, mount state and
holders before reads. The installed `dd` is GNU coreutils 9.4. No partition
output path or write operation is constructed on the phone.

Run from a local Mac Terminal when the phone's sudo password is available:

[source,sh]
----
python3 support/experimental-devices/unihertz-titan/tools/acquire-partitions.py \
  --sudo --output /absolute/private/new-installed-images
----

The password prompt is local and hidden; the password goes only to sudo's stdin
over the selected USB transport. Do not send it in chat. Omitting `--sudo` uses
the current shell's permissions. The destination must be new and outside Git.
Directories are `0700` and files `0600`. Partial, oversized, short or failed
transfers are not promoted to complete images. Exact byte counts, Mac hashes and
an independent phone-side hash are required; repeat reads establish agreement,
not atomicity or a tested restore. The private manifest must be inspected before
any findings are published.

After successful acquisition, inspect installed boot with `--check-titan`,
recovery with generic `inspect-boot-image.py`, and dtbo using the inspector's DT
table parser. Compare whole-image hashes with the candidates, then compare kernel,
ramdisk, DTB and AVB sections if they differ. A profile mismatch must be retained
as evidence; never modify a backup to make it satisfy the reference profile.

==== Sparse userdata backup feasibility

A follow-up rechecked `df`: 8262604 KiB used, 106356912 KiB available on userdata.
The phone already has e2image 1.47.0 and Zstandard 1.5.5. No phone software was
installed. The Mac has e2fsprogs and Zstandard, and a same-size synthetic sparse
file (119878418432 logical bytes) occupied only 32768 bytes on its local
filesystem. This checks hole support, not the backup size of actual phone data.

The link:https://github.com/tytso/e2fsprogs/blob/v1.47.0/misc/e2image.8.in[matching e2image manual]
documents `-r -a` for copying filesystem metadata and file data while omitting
unused blocks. The `-a` is essential: the default image contains metadata only.
This is a filesystem backup, not a byte-for-byte or forensic partition copy;
partition geometry and any data outside the filesystem need separate accounting.
Do not replace the exact boot/recovery/dtbo backups with this method.

Raw output can stream to stdout; QCOW2 creation requires a seekable output and
cannot use this pipe. The
link:https://github.com/tytso/e2fsprogs/blob/v1.47.0/misc/e2image.c#L658[raw stdout implementation]
emits zero bytes for skipped blocks, so compress on the phone before transport.
Save the compressed stream privately on the Mac, then decompress with sparse
output support when inspecting a working copy. This avoids a fully allocated
120 GB temporary file and avoids staging a backup on the phone's source
filesystem. Transferring a sparse file without preserving holes can expand it.

An entirely local 256 MiB ext4 fixture exercised `e2image -ra SOURCE -`, streamed
Zstandard compression, and `zstd -d --sparse` into a new ordinary image file.
The compressed output was 1064951 bytes; the restored image retained its
268435456-byte logical size while allocating 27148288 bytes. A read-only
`e2fsck -fn` passed. Extracted payload bytes matched, mode `0640` survived,
two hardlinks retained one inode, and the symlink survived. These synthetic
numbers are not a phone-backup size estimate or a Titan restore test.

With about 7.9 GiB currently used, a sparse/compressed filesystem backup is
plausibly within the Mac's roughly 30 GiB free space. Measure metadata/allocated
blocks and enforce output/free-space limits before acquisition; budget for both
the archive and any sparse verification copy. Do not promise an exact final size
from `df` alone.

The remaining gate is consistency. `e2image` normally refuses a source mounted
read-write; `-f` would bypass that protection and must not be used for this
preservation plan. Userdata is still mounted writable, so no actual userdata
image was acquired. A separately approved quiescent/read-only environment is
needed before running the proposed pipeline. Sparse allocation solves the host
space problem without solving concurrent filesystem or calibration writes.

A consistent full backup requires a separately authorized maintenance procedure:
stop all writers, including Android/modem services where relevant, and acquire
from an environment that leaves the targets unmounted. Inspect all relevant
mount namespaces, holders and raw writers. Do not silently freeze, unmount or
stop services during this read-only session. A filesystem-level export must
preserve metadata and be paired with an explicitly reviewed reconstruction plan;
copying home alone omits Nix, Android data and writable system state.

Retain a second verified copy on separate storage. Verify hashes again after
copying, and keep originals immutable during inspection. Linux ext4 can replay
its journal even with `ro`; use read-only block backing plus `ro,noload` when
examining a copy, and run any repair only on a disposable copy. See
link:https://docs.kernel.org/admin-guide/ext4.html[the ext4 documentation] and
link:https://docs.kernel.org/driver-api/mmc/mmc-dev-parts.html[eMMC boot partitions].

=== Recovery procedure to review before any mode change

The downloaded recovery candidate was also inspected without executing or
extracting its contents. Its gzip ramdisk expands to a 36072960-byte newc archive

boot this recovery for passive inspection or offline preservation. These findings
apply to the public candidate. The different installed recovery is described
