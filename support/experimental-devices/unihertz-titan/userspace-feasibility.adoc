Research date: 2026-10-15. This record narrows the M2 userspace question for the
installed Ubuntu Touch kernel. It is based on upstream documentation, Nix
evaluation, pinned sources and earlier read-only phone measurements. No NixOS
system or generated image has booted on the Titan; nothing here is a boot result.

== Question

Can a Mobile NixOS userspace run on the installed reconstructed Linux
`4.14.141+` kernel (runtime configuration SHA-256
`1113327761998175c8cc78dbce10ac23c7fed8a8418f1072e553e8c0acc4286b`) without
kernel work, and if so, with which package set?

and lacks required functionality. Below the recommended baseline, it sets the
`old-kernel` taint and "will most likely still function", with limited support.

|link:{sd}/v258/README[258]–link:{sd}/v259/README[259] |5.4 |5.7 |Unsupported
|link:{sd}/v260/README[260]–link:{sd}/v261/README[261] |5.10 |5.14 |Unsupported

The v261 minimum explicitly covers pidfd (5.4), `STATX_ATTR_MOUNT_ROOT` (5.8),
`close_range()` (5.9) and `STATX_MNT_ID` (5.10), all absent in the measurements
above. Versions 255, 257 and 261 also list `CONFIG_FHANDLE` as a required option.
The running Ubuntu Touch manager shows that this listing is not an immediate
PID 1 failure for Ubuntu's 255 build; it does not show which udev, mount or
service operations degrade.

== Findings

. *Current userspace on the installed kernel: not viable without kernel work.*
  Every currently supported NixOS package set uses a systemd whose documented
  minimum baseline excludes Linux 4.14. The direct probes confirm several of
  the missing baseline interfaces, and the v261 source references in the API
  record show hard failures in path traversal, child tracking and service
  execution. Version 260 was not separately traced.
  Stage 1 uses `systemdMinimal` of the same version, so replacing only stage 2
  does not avoid the gap.
. *Older userspace: possible experiment, not a support path.* Only package sets
  with systemd 257 or older place 4.14 above the minimum baseline, and all have
  passed their support periods. The last such repository pin is `4d90c64e742e`
  (systemd 257.6), an unstable snapshot. Version 257 recommends 5.4 and
  255/256 recommend 4.15, so even these run tainted and with reduced
  functionality. Ubuntu Touch's working 255 manager makes a bounded boot
  experiment plausible; it does not validate a NixOS configuration, udev rules,
  mount handling or service isolation. Any such experiment needs the explicit
  maintenance/security assessment required by the porting plan.
. *Kernel backports: open-ended.* Meeting the v260/v261 minimum would require at
  least pidfd, `close_range()`, `statx` mount-ID and mount-root support, the
  mount API and other post-4.14 interfaces in the reconstructed vendor tree, in
  addition to configuration changes. This is substantial kernel development on
  an unmaintained Android 4.14 base.
. *Native kernel route: consistent with current userspace and upstream policy.*
  A modern MT6771 kernel removes the baseline conflict but needs board
  bring-up; the porting plan's N0 audit applies. The recovery prerequisites
  below are shared by both routes.

== Recommendation for decision D1

Do not plan M2 around the current package set on the installed 4.14 kernel.
For sustained work, prefer the native route (N0/N1). A downstream boot on the
old kernel is justified only as a separately bounded diagnostic experiment with
an explicitly unsupported package set (systemd 257 or older), isolated from the
current tree's assumptions, and only after the recovery gates in
link:recovery-preparation.adoc[the recovery record] are met. The owner records
the final D1 decision; this record supplies the evidence for it.

Evidence that would change this assessment: a maintained package set whose
systemd supports 4.14, verified kernel backports passing the systemd test suite
on the Titan, or hardware results showing that the native route is blocked.
