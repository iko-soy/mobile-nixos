= Experimental USB probe initramfs

`usbProbe.ramdisk` is a separate, build-only AArch64 initramfs for a first
temporary boot of a new ramdisk on the Titan, as Stage B of the
link:../temporary-boot-trial.adoc[temporary boot proposal]. It reports over USB
and then reboots by itself. It does not replace `rescue.ramdisk` or the USB
acquisition profile. On 2026-10-15 Stage B sent its envelope with `fastboot
boot`, but the bootloader crashed before starting it, so the probe has never
run on the Titan. Building it does not authorize booting it.

[source,sh]
----
# Run on the x86_64 Linux builder, from the repository root.
nix-build support/experimental-devices/unihertz-titan -A usbProbe.ramdisk --no-out-link
nix-build support/experimental-devices/unihertz-titan -A usbProbe.vmTests --no-out-link
----

== Behavior

The ramdisk holds only one static program, the rescue PID 1 built with the probe
profile. Before any mount or device access, PID 1 starts a separate deadline
process. That process keeps only the descriptors PID 1 inherited from the
kernel, blocks every signal it can and sleeps until 150 seconds after PID 1
started, by `CLOCK_BOOTTIME`; it then writes one console line, syncs and
requests an ordinary restart without an argument. PID 1 itself restarts ten
seconds later if that has not happened, from its wait loops, including the
failure path; only the USB owner's bounded port polling during setup, at most
30 seconds, does not check. If the clock or the deadline process is
unavailable, PID 1 restarts at once. The restart code refuses to run unless it
is PID 1 or a child of PID 1, and `main` refuses to start outside PID 1 before
any of it can run, so starting the program on another machine, as the
qemu-user check does, cannot reboot that machine.

PID 1 then does what the default rescue profile does: it mounts only the
virtual filesystems, sets and verifies the kernel read-only flag on every block
device and waits for the complete measured eMMC set. It binds the fixed ACM
gadget of the link:../usb-pipeline/README.adoc[USB acquisition profile], with
the same controller identity, descriptors and seven-mount policy. Every two
seconds it rechecks the gadget, guards every block device again and writes one
line to the gadget:

[source,text]
----
TITAN_PROBE v1 seq=<n> uptime=<s> deadline=<s> kernel=<release> storage=guarded usb=bound
----

The kernel release is restricted to letters, digits and `.+_-`. The line holds
no serial number, partition data or other identifier. Writes never block. With
no host reading, lines queue in the gadget driver's buffer; after a short or
refused write, queued output is discarded so that a later host receives whole
lines. Any failure is
reported on the console and leaves PID 1 waiting for the deadline restart. The
probe reads no storage contents, accepts no input and starts no acquisition,
shell, network or Android service.

The restart is the same kind as an ordinary `reboot` from Ubuntu Touch, whose
effect on this phone Stage A's final step observes. A kernel panic instead
triggers the vendor exception handler's watchdog reset, after which the
bootloader's behavior is unknown.

== Disposable VM checks

The VM profile substitutes the virtio disk `vda`, the `dummy_udc` controller,
a 45-second deadline and five-second discovery. It reads the report back
through the guest's own `cdc_acm` host port. QEMU runs with `-no-reboot`, so a
guest restart ends the process; each case must end that way by itself, after
its deadline and within 40 seconds of it, with the kernel's restart message and
an unchanged writable disk fixture.

[cols="1,3",options="header"]
|===
|Case |Required observation
|`valid`
|USB bound, three report lines received in the guest, then the deadline
process's restart; no failure or backstop marker.
|`stuck`
|PID 1 blocks forever after binding USB; the deadline process still restarts
the guest on time.
|`child-killed`
|The deadline process is killed first; PID 1's backstop restarts the guest ten
seconds after the deadline.
|`missing-disk`
|Storage discovery fails before USB setup; the deadline process restarts the
guest on time.
|===

The production build check rejects dynamic dependencies and any VM-only string,
such as the case selector, `dummy_udc`, `ttyACM0` or `/dev/vda`. A qemu-user
check confirms that the AArch64 program refuses to run as anything but PID 1.

== Known limitations

An independent review on 2026-10-15 found no high or medium problems and these
low-severity limits, left for the next revision of the probe:

* Both restart paths write a console line with blocking calls and then share
  the same `reboot()` call, so the PID 1 backstop covers a dead or stuck
  deadline process, not a stalled console or a hung kernel restart.
* The VM checks measure the restart from QEMU's start, which includes guest
  boot time, and do not compare the armed deadline with PID 1's start; the
  phone's 150- and 10-second constants have no automated check.
* The envelope inherits `panic=0` from the rescue command line, removing the
  kernel's own panic restart as a fallback behind the vendor watchdog reset.
* After a USB reset or re-enumeration the gadget TTY may hang up; the probe then
  stops reporting and waits for its deadline.

== Hardware boundary

The x86_64 VM kernel does not exercise the Titan's vendor 4.14 kernel, its
MTU3 USB controller, macOS enumeration, the vendor restart path, watchdogs or
charging. A guarded storage set does not establish quiescence of firmware or
kernel writers. The Mac-side `tools/read-probe-report.py` only listens: it waits
for exactly one USB device with the gadget's fixed manufacturer, product and
serial strings, reads its modem port in raw mode and validates the lines. The
USB ID `1209:0005` alone is not enough, because Ubuntu Touch's own gadget on
this phone uses it too.
