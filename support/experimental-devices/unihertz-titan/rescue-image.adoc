= Private rescue boot-image envelope

This local packaging experiment combines the preserved installed boot image's
kernel and DTB with the separately reviewed AArch64 USB acquisition ramdisk. An
x86_64 VM-test variant of that ramdisk's sources passed its disposable VM cases;
the AArch64 binaries themselves ran only qemu-user refusal checks. It creates
an unsigned Android v2 image for inspection. It supplies no phone command,
bootloader acceptance evidence, installation procedure or recovery guarantee.
No generated image has booted on the Titan, and this does not boot NixOS.

== Fixed inputs and private output

`tools/prepare-rescue-image.py` accepts only the recorded 33554432-byte installed
boot image with SHA-256
`6829a8bcaa696a6fe283184a874450357dd81e7e203eedaf79329bdc55745e83`
and the corrected 3055279-byte USB acquisition ramdisk with SHA-256
`0ed6d547c282b8a93d206d747cdb2b5535a7175726265f04e8085fb62671eb74`. The earlier
3054712-byte build (`27d2a3da...`) contains the mount-ID-0 and zram defects found
by the 2026-10-15 audit; an intermediate corrected build (`65ac5adf...`) lacked
the later readiness and re-guard changes. Neither is accepted.
With `--ramdisk-profile usb-probe`, the helper instead accepts only the
65825-byte second-version link:usb-probe/README.adoc[USB probe ramdisk] with
SHA-256 `cdb87d510caffe98fca0c009cecd31016e0cc85b9fd08c7cd41d7a8c6bad3a99`,
checked by the archive inspector's separate one-executable `usb-probe` profile,
and writes the probe's own command line, which ends in `panic=5` instead of
`panic=0`. The first version's ramdisk (65652 bytes, `8b45b35e...`) is
superseded. For the probe only, `--recovery` with the preserved stock recovery
(`4dd1c1f7...`) selects the recovery-partition layout: the helper copies that
image's 47545-byte recovery-DTBO section (`0da3565a...`, identical to the dtbo
partition's table) into the new image, as the stock recovery carries it.
With `--ramdisk-profile usb-control`, the helper accepts only the 3773960-byte
link:control/README.adoc[offline control-region acquisition ramdisk] with
SHA-256 `14a573ef702b5bf1a85abcbdd634cf780d9403c64e8bc5829708810964757d48`,
checked by the inspector's `usb-control` profile; it uses the probe's command
line and may use the same recovery layout. With the probe profile in the
recovery layout only, `--kernel` replaces the installed kernel with the pinned repository-built
`Image.gz` (9532189 bytes, `cd370ef6...`), whose decompressed `Image`
(`34a45c8a...`) it also checks; the DTB and all other fields stay. That
recovery-layout envelope is 9764864 bytes, SHA-256
`35fb8d6427b3b32809b48789235158fda460b5d6e6ecbf4ed703ed0f3694050f`,
byte-identical to the pinned `mkbootimg`, for the
link:repo-kernel-trial.adoc[repository-kernel trial].
These constants select reviewed inputs; there is no runtime hash, source-profile
or command-line override. A future ramdisk build requires a reviewed profile
update. Matching a digest establishes byte identity, not hardware suitability.

The helper runs locally against private regular files. It does not import them
into the Nix store, invoke a phone transport or execute their contents. Inputs
and outputs must remain outside Git checkouts and `/nix`. It creates a new
private output directory and never overwrites an existing destination.

[source,sh]
----
python3 support/experimental-devices/unihertz-titan/tools/prepare-rescue-image.py \
  --boot /absolute/private/installed/boot.img \
  --ramdisk /absolute/private/usb-acquisition/initramfs.cpio.gz \
  --output /absolute/private/new-rescue-envelope
----

The output `UNTESTED-UNSIGNED-rescue.img` ends after the page-aligned DTB. It is
not padded to partition size and has no AVB footer, vbmeta block or signature.
The accompanying manifest records inputs, sections, command-line policy and the
expected image hash; the helper verifies the saved bytes by readback before
publishing, but that readback result is not a manifest field. Keep these files
private with the retained originals.

== Preserved fields and changed startup arguments

The fixed installed profile has Android header v2, a 1660-byte header and
2048-byte pages, an empty board name, and no second-stage or recovery-DTBO
payload. Load addresses remain kernel `0x40080000`, ramdisk `0x55000000`,
tags/DTB `0x54000000`, and second stage zero. The kernel and 112135-byte Android
DT table are copied byte-for-byte. The OS `10.0.0` and patch `2025-08` fields are
inherited packaging metadata, not a security-support claim for rescue userspace.
The legacy image ID is recomputed; that SHA-1 format checksum is not authentication.

The new fixed header command line is:

[source,text]
----
bootopt=64S3,32N2,64N2 buildvariant=user security=apparmor rodata=0 rdinit=/init init=/init panic=0
----

Ubuntu Touch's `systempart` and `halium_lvm_vg` arguments are removed. The
independent ramdisk's `/init` is selected explicitly. `rodata=0` is retained as
an inherited vendor-kernel compatibility assumption; its necessity has not been
demonstrated. `panic=0` requests no ordinary panic-timer reboot, but it does not
keep this kernel halted. With the preserved configuration
(`CONFIG_MTK_AEE_IPANIC=y`), the pinned vendor exception handler registers panic
and oops notifiers that request an immediate watchdog reset before the panic
timeout is consulted. This is source and configuration analysis, not a hardware
observation. How the bootloader treats that exception reset is unknown,
including possible dump writes to regions without a private copy, such as
`expdb`, and whether it boots the same image again. `panic=0` also does not
address charging behavior or power failure handling.

The unchanged DTB also contains `/chosen/bootargs`:

[source,text]
----
console=tty0 console=ttyS0,921600n1 vmalloc=400M slub_debug=OFZPU swiotlb=noforce page_owner=on cgroup.memory=nosocket,nokmem androidboot.hardware=mt6771 firmware_class.path=/vendor/firmware loop.max_part=7
----

Those bytes contain no `root=`, `init=`, `rdinit=`, `skip_initramfs` or `panic=`
override. The firmware search path does not mount vendor storage by itself. Neither this
observation nor unchanged kernel/DTB bytes establishes absence of early kernel
or firmware storage activity. Bootloader argument merging and the effective
command line of a rescue boot remain unverified.

== Format checks and limits

The separate `tools/inspect-rescue-ramdisk.py` checks a bounded single-member
gzip stream and its exact newc archive profile: only the expected directories
and six static AArch64 executables, with no overlay, extra archive, symlink,
device node or alternate init. It computes payload hashes; supplying both build
manifests additionally checks their agreement with the parsed bytes. Neither
check establishes the behavior of arbitrary machine code. The repacker also
requires the fixed reviewed ramdisk hash above.

[source,sh]
----
python3 support/experimental-devices/unihertz-titan/tools/inspect-rescue-ramdisk.py \
  /absolute/private/usb-acquisition/initramfs.cpio.gz \
  --sha256sums /absolute/private/usb-acquisition/SHA256SUMS \
  --payload-sha256sums /absolute/private/usb-acquisition/payload-SHA256SUMS
----

The new image is checked with the repository's generic boot inspector. It
deliberately does not satisfy that inspector's `--check-titan` requirement for
the Ubuntu Touch reference package's appended footer. Do not relax that existing
profile or treat its expected rejection as a malformed raw boot envelope.

The first private Mac packaging run produced 12707840 bytes with SHA-256
`87caa6956fb512d61d466fca6b3e92c524480c5e921fbb18656743e6aecae5d5`. It embeds the
defective `27d2a3da...` ramdisk: it would stop at its first mount check on the
Titan and must not be used. It is retained privately only as historical
evidence. On 2026-10-15 the helper repackaged the final corrected ramdisk, also
12707840 bytes, with SHA-256
`52f48e749024c97a0582b718b6c5188c27eb8e2fcdd5553205e59d42a2923dd3`; an
intermediate envelope (`694869a4...`) from the superseded `65ac5adf...` ramdisk is
retained privately only as evidence. For each envelope a separate invocation of
the pinned LineageOS `mkbootimg.py` at revision
`40a19c4c5ffe8b86c6c61318c8aa4ffe35d6e7ad` produced identical bytes from the
same preserved kernel, DTB and ramdisk. Independent readback verified the image
hash, unchanged input hashes, directory mode `0700` and file mode `0600`.
The same day the helper packaged the first probe ramdisk into a 9719808-byte
envelope with SHA-256
`e6da06fc1f6c47d4c4ae0edc8c1888e9dc628dbef9b8f8a01ae37768065704c8`, sent in
Stage B of the link:temporary-boot-trial.adoc[temporary boot trial], and then
the second version into a 9719808-byte envelope with SHA-256
`11acc288e8b0b56cf47a1d885fec3dfd38bc831dc37f6dea04619895ed2c383b`, which the
link:recovery-route-trial.adoc[recovery-route proposal] superseded with a
9768960-byte recovery-layout image, SHA-256
`f37dd3b159226e7c9955ee87246a570b8075d6e95187d4f1406d456f5c0ce59d`, which it
pins. The pinned `mkbootimg`, given the same section as `--recovery_dtbo` for
the last, produced identical bytes for all three.
The generic inspector accepted its geometry; the reference-profile check
rejected only the intentionally absent AVB footer/vbmeta. Both build manifests
also matched the independently parsed ramdisk and its six ELF payloads.

For the first envelope, at commit `bae47c7a`, all 186 host tools tests and the
existing boot-packaging fixture passed through Nix on the Mac, including 15
archive-inspector and 18 rescue-envelope tests.
The independent synthetic `mkbootimg.py` comparison ran without a skip.
Synthetic filesystem fixtures use private temporary directories outside `/nix`
so that the production helper's Nix-path refusal remains exercised unchanged.

The existing GSI vbmeta must not be copied onto the changed image. Its flags and
descriptors do not authenticate this rescue payload. This experiment also does
not invent a replacement AVB trust/rollback policy. See the
https://android.googlesource.com/platform/system/tools/mkbootimg/+/refs/heads/main/include/bootimg/bootimg.h[Android boot-header definition]
and https://android.googlesource.com/platform/external/avb/+/refs/heads/main/README.md[AOSP AVB documentation]
for the distinction between layout, hash descriptors and bootloader policy.

Before any rescue boot, the staged order in
link:recovery-preparation.adoc[the recovery record] applies: a verified entry
and return, bootloader identity and acceptance review, separately authorized
temporary boot if supported, transport readiness and reviewed failure behavior.
Writer quiescence and consistent userdata/calibration preservation are what the
booted environment must then establish and check; rollback writes stay gated on
them. Building or inspecting this envelope supplies none of those permissions
or runtime results.

This envelope is not proposed for a first boot: its ramdisk copies userdata,
which the owner decided on 2026-10-15 not to preserve, and it never reboots by
itself. The link:temporary-boot-trial.adoc[temporary boot proposal] starts
with the installed image and defers new ramdisks to a self-rebooting probe
profile.
