= Remaining consistent preservation requirements

Research date: 2026-10-15. This record lists what still has to be preserved
before any later rollback write, and the conditions under which a copy counts as
consistent. It adds no acquisition and authorizes no phone action. See
link:backup-catalog.adoc[the backup catalog] for what is already preserved and
link:recovery-preparation.adoc[the recovery record] for the staged procedure.

*Owner decision, 2026-10-15: userdata is not to be preserved.* The owner does
not need its contents, so the requirements below cover the sixteen other
regions. Earlier records that require consistent userdata preservation are
superseded on that point. The decision limits what is copied, not what is
allowed: userdata is still never written, formatted or wiped without separate
authorization, and a later write or recovery boot that damages it would lose its
contents for good.

RPMB is not ordinary block data, has not been opened and is out of scope.

== What counts as a consistent copy

A copy of a region is consistent only when all of the following hold for the
whole acquisition window:

. *No writers.* No Ubuntu Touch services, LXC/Android container, Android
  hardware services, modem userspace or NVRAM services are running, and no
  filesystem on the target is mounted in any namespace. The rescue profile must
  not start the modem: read `/sys/kernel/ccci/boot` only as recorded in the
  recovery record, and never open CCCI character devices.
. *Read-only enforcement.* Every visible block node carries the kernel
  read-only flag before content reads, as the rescue PID 1 already requires.
  This does not stop firmware or bootloader writers, so the environment must
  also not have started them.
. *Fixed identity.* Each target matches its recorded GPT number, label, start,
  length and parent disk before and after reading.
. *Stability.* Raw regions have matching before/after hashes from independent
  reads. ext4 regions must report a clean state with no pending journal
  recovery or orphan cleanup; they must not be repaired, replayed or mounted
  writable to pass. Inspect copies with read-only backing and `ro,noload`.
. *Verified transfer.* Bytes are length- and hash-verified on the Mac before
  completion is acknowledged, as the TTR1 transport does.
. *Retention.* Two verified copies on separate storage. Only the Mac copy exists;
  the owner has no second destination, so this requirement stays open.

A shutdown or abrupt reset of the live system does not by itself establish
these conditions. Stable normal-mode hashes of unmounted regions show stability
during the reads, not absence of writers before or after them.

== Gaps in the current build-only tooling

* The integrated link:usb-pipeline/README.adoc[USB acquisition profile] selects
  only `userdata`, which is no longer to be preserved. No fixed raw-region
  producer exists yet for the sixteen calibration and control regions in the
  same offline environment; that is now the producer the offline boot needs.
* No rescue image has been accepted or booted by the installed bootloader, and
  the USB ACM path has not been recognized by the Mac. Entry to bootloader
  fastboot and the return from it worked once in the
  link:entry-return-trial.adoc[entry and return trial]; a rescue boot and its
  return remain unverified.
* The four mounted ext4 regions need a clean-state check like the userdata
  guard; raw copies of them are small, so a sparse filesystem image is not
  required.

== Ordering

This sequence keeps the dependencies one-directional:

. Done on 2026-10-15: the link:entry-return-trial.adoc[entry and return
  trial]. It sent no image and wrote no partition by intent.
. Done on 2026-10-15, before and after that trial: the fixed
  link:control-region-preservation.adoc[normal-mode reads of the twelve
  unmounted regions]. Only `expdb` differed afterwards. These are not
  consistent copies.
. A reviewed and separately authorized temporary boot of the rescue image,
  loaded into RAM only, to establish acceptance, USB recognition and the return
  path.
. A reviewed offline acquisition boot that meets the conditions above for the
  sixteen regions other than `userdata`, with a demonstrated return.
. Only then any rollback write, separately authorized.
