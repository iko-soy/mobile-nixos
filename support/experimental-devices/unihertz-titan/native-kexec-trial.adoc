= Kexec CPU trial

Status on 2026-10-16: *run once with the owner's explicit approval; the CPU
restart test answered the question, so both kexecs were skipped as the
procedure requires. See <<result,the result>>.* Each repetition needs the
owner's explicit approval of this exact procedure.

The link:native-ram-env-trial.adoc[working-environment trial] ran the first
kexec on the Titan: through `kexec_file_load`, reusing the bootloader's tree,
it booted the same kernel and stage 0 without the bootloader, but only CPU 0
came back, and the kernel log had wrapped before the secondary CPUs' messages.
The saved logs show that each of the seven secondary CPUs timed out after
five seconds rather than being refused by the firmware. This trial runs the
same system with a 4 MiB kernel log. It first takes one A53 and one A73 core
offline and back in the healthy first boot: the same firmware calls a kexec
makes (PSCI CPU_OFF and CPU_ON), from the bootloader's kernel address, with
the log readable. If a core does not come back, the firmware cannot restart a
core it has turned off, which explains the kexec result without another
kexec. If both come back, it kexecs through `kexec_load` with a copy of the
running tree and then, if that system's reserved memory is unchanged,
through `kexec_file_load`. Every boot's complete kernel log, memory map and
CPU state are saved. Neither kexec path can place the kernel where the
bootloader does (`0x40080000`, not 2 MiB aligned), so a kexec failure alone
cannot tell a wrong address from a firmware that does not restart cores. The original
recovery is then restored. Ubuntu Touch's boot and `dtbo` partitions are never
written, and Linux never sees the phone's storage.

== Result (2026-10-16)

The owner approved the procedure and ran the partition reads, the entries, the
Volume Up start and the unlocks; watchers ran the fastboot steps, the push and
the USB log, and the session ran over SSH from the Mac.

* *Preconditions.* The baseline found the battery full and charging, no
  update pending or running and empty recovery command directories; its one
  failed unit, `console-setup`, had failed in both earlier baselines too.
  Step 2 found boot, recovery and dtbo identical to their preserved copies,
  and no control region changed since the latest copy.
* *Part 1.* `fastboot flash recovery` reported `Writing 'recovery' OKAY`, and
  step 7 read recovery back as `1b586f60...`, with boot and dtbo unchanged.
* *Question 1, yes.* After the Volume Up start the boot ROM and preloader
  passed through, and the image's USB device appeared 50 seconds after Ubuntu
  Touch left. Stage 0 verified the pushed store, SSH answered by 48 seconds
  of uptime, and `titan-session end-in 40` moved the end to 2448 seconds. The
  kernel log was complete from `[    0.000000]` and reported `log buffer data
  + meta data: 4194304 + 14680064 = 18874368 bytes`. The firmware reported
  PSCI 1.0 and SMC Calling Convention 1.1, KASLR was off for lack of a seed,
  and the kernel's code sat at `0x40080000`-`0x4211ffff`. All eight CPUs came
  up within 10 ms: cpu0 to cpu3 are Cortex-A53, cpu4 to cpu7 Cortex-A73.
  NixOS was `running` with no failed unit, at 35 °C, and the command line
  carried every setting the records require. macOS re-enumerated the device
  for two seconds at 54 seconds of uptime, with no reset on the phone; the
  first attempt at the records failed on the missing link address and was
  repeated.
* *Question 2, no.* Writing `0` to cpu1's `online` took it offline, and the
  kernel logged `psci: CPU1 killed (polled 0 ms)`: the firmware reported the
  core off at once. Writing `1` failed after 5.3 seconds with `CPU1: failed to
  come online` and `CPU1: failed in unknown state : 0x0`. No `psci: failed to
  boot` line appeared, so the firmware's CPU_ON call returned success, but the
  core never reached the kernel's entry code, not even far enough to record a
  failure. This is the five-second timeout that the seven secondary CPUs met
  after the working-environment trial's kexec, here with the kernel at the
  bootloader's own address and no kexec. The system stayed `running` on seven
  CPUs, at 35 °C, with no further kernel message. As the procedure requires,
  cpu4 was not tried and neither kexec ran; the failed core also counts as
  stuck, so this kernel would have refused any kexec.
* *Questions 3 and 4.* Not run, as above.
* *Question 5, yes.* `titan-session end-in 1` at 139 seconds of uptime moved
  the restart to 199 seconds; the image's device left 77 seconds later, the
  preloader passed through, and Ubuntu Touch booted (`bootreason=reboot`).
  From Ubuntu Touch, `sudo /sbin/reboot bootloader` reached fastboot, the
  preserved original was written (`Writing 'recovery' OKAY`) and Ubuntu Touch
  returned. The read-back found recovery `4dd1c1f7...`, with boot and dtbo
  unchanged throughout; of the control regions only `expdb` changed, as after
  every boot.

Afterwards, read-only over ADB: Ubuntu Touch kept all eight CPUs online
through a 20-second sample, and its kernel registers CPU hotplug callbacks
that the native kernel lacks: `hps/cpuhotplug`, `ppm/cpuhp` and two
`mcdi_cb` states, one among the teardown states and one among the bring-up
states. They belong to MediaTek's hotplug policy, performance and power
manager and multi-core deep idle (MCDI) drivers; whether the MCDI callbacks
are what lets a core restart is not shown.

The session data and kernel logs are in the private evidence directory. This
shows that on the Titan the native kernel cannot restart a secondary CPU it
has turned off through PSCI, for a kexec or for CPU hotplug alike, and that
the kernel's placement is not the cause. A kexec therefore leaves the next
kernel with CPU 0 only, after a five-second wait for each other core, and
that kernel refuses any further kexec, since it counts the cores as stuck.
Next: read what the MCDI hotplug callbacks do in MediaTek's kernel source for
the MT6771; and, for kexec in the meantime, consider letting `titan-kexec`
start kernels with `nosmp`, so that they skip the cores, boot without the
wait and can kexec again.

== Procedure

*Part 1: write the image.* Steps 1 to 7 of the
link:repo-kernel-trial.adoc[repository-kernel trial], with `--profile
ram-nixos-3` and the image
`native-ram-image-v4/UNTESTED-UNSIGNED-native-ram.img`; step 7 must read
recovery back as `1b586f60...`, with boot and dtbo unchanged.

*Part 2: run the session.*

[start=8]
. *Listen:* start `tools/ram-nixos.py` as its own job, which reports as soon
  as SSH answers, with the private copy of the store squashfs, its pinned size
  and SHA-256, a new private output directory and the dedicated key; and a
  watcher that records every USB device change and whether Ubuntu Touch or
  fastboot appears after the image.
. *Start, owner-run:* keep the cable connected, power the phone off from
  Ubuntu Touch, hold Volume Up and press Power, and release both once the
  unlocked-state warning appears; allow the accessory if macOS asks. No
  confirmation is needed: the session starts when SSH answers.
. *Session:* at once and only once `titan-session end-in 40`; then the
  records below. Read-only as in the working-environment trial: nothing
  written in sysfs, debugfs or configfs, and no debugfs register dumps, with
  the one exception of the next step.
+
*Records of each boot*, saved privately: `titan-session status`; the CPUs'
`online`, `offline`, `possible` and `present` lists; the complete kernel log,
which must start at `[    0.000000]` and report its buffer as `log buffer
data + meta data: 4194304 + ...`, with its `psci:`, `CPU`, `smp:`, KASLR and
`OF: reserved mem` lines; `/proc/iomem`, with its `Kernel code` lines; the
reserved-memory nodes of `/proc/device-tree`; the command line, which must
carry `nbd.nbds_max=0`, `panic_on_oops=1`, `log_buf_len=4M` and, after each
kexec, its marker; and the CPU temperature.
. *CPU restart test, writing sysfs:* for cpu1 (A53) and then cpu4 (A73),
  write `0` to `/sys/devices/system/cpu/cpuN/online`, check that it reads
  `0`, write `1` and check that it reads `1`, saving the kernel log after
  each core. If a core does not come back online, record it and go to the
  end step without a kexec.
. *Kexec A, `kexec_load` with the running tree:* copy the payload's `Image`
  and `initramfs.cpio.gz` into `/run/kexec` over SSH and the running tree with
  `cp /sys/firmware/fdt /run/kexec/fdt.dtb`; run `strace -f -e
  trace=kexec_load,kexec_file_load titan-kexec --dtb /run/kexec/fdt.dtb <its
  SHA-256> /run/kexec/Image <its SHA-256> /run/kexec/initramfs.cpio.gz <its
  SHA-256> titan_kexec=a`, which must show `kexec_load` and its segments'
  addresses; then `systemctl kexec`. Once the image's USB device has left,
  start `tools/ram-nixos.py` again as its own job with a new output
  directory. The kexec-tools purgatory checks the segments' SHA-256 with the
  caches off, which may take minutes; the watcher records when the device
  leaves and returns. Expected: the device returns, stage 0 takes the push
  and SSH answers; then the records.
. *Kexec B, `kexec_file_load`:* only if the system from kexec A runs,
  answers SSH, and shows the same `OF: reserved mem` lines and reserved-memory
  nodes as the first boot. Copy the payload into `/run/kexec` again; run
  `titan-kexec /run/kexec/Image <its SHA-256> /run/kexec/initramfs.cpio.gz
  <its SHA-256> titan_kexec=b` under the same `strace`, which must show
  `kexec_file_load`. If kexec A brought up fewer than eight CPUs, the kernel
  is expected to refuse this load with "Can't kexec: CPUs are stuck in the
  kernel."; record the output and go to the end. Otherwise `systemctl kexec`,
  the push helper as its own job once the device has left, and the records.
. *End:* `titan-session end-in 1`; the session deadline must restart the
  phone into Ubuntu Touch within about two minutes. Only if it has not after
  three minutes, `titan-session end`.

*Part 3: restore.* From Ubuntu Touch, `sudo /sbin/reboot bootloader`
(owner-run); then, as in the earlier trials, write the preserved original
with the `original-recovery` profile, return, and read recovery back as
`4dd1c1f7...`, with boot and dtbo unchanged.

*Part 4: compare.* A normal-mode control-region copy after Part 3, compared
with the one from step 2 (`expdb` changes on every boot).

== Residual risks

* The CPU restart test writes two sysfs files, an exception to the read-only
  sessions: it turns one A53 and one A73 core off and on through the
  firmware, as a kexec does. A core that does not come back stays off or is
  counted as stuck, which only blocks later kexecs; an oops panics and
  restarts the phone.
* Kexec has run once on this phone, through `kexec_file_load`, and lost the
  secondary CPUs. The tree-replacing `kexec_load` path has not run anywhere:
  the VM's kexec uses `kexec_file_load`, and checks only that `--dtb` refuses
  a tree with the wrong hash. Its purgatory checks the segments' SHA-256 with
  the caches off, which is slow.
* Kexec B may start from a kernel whose secondary CPUs did not come up. If
  one is stuck in the kernel, arm64 refuses to load a kexec image, so
  `titan-kexec` fails and the session goes to the end; if they are merely off,
  the next kernel asks the firmware to start them again.
* As in the working-environment trial: devices left in states the next kernel
  does not expect (the USB gadget is detached before each kexec), a hang from
  a shutdown until the next stage 0 without any deadline, sessions with no
  frequency scaling, throttling or charger driver, and the first boot's
  residual risks.

== What this can and cannot show

Success tells whether either kexec path brings the secondary CPUs back on the
Titan, with the kernel's own account and the physical placement of each
kernel, which decides how to make kexec usable for trying new kernels and
trees. It does not show a kexec with a modified tree.
