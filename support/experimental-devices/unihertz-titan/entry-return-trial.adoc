= Bootloader entry and return trial

Status: *run once on 2026-10-15 with the owner's explicit approval; see
<<result,the result>>.* The procedure changes the phone's boot mode twice, so
each repetition needs the owner's approval of this exact procedure. It sends no
image and issues no flash, erase, `oem`, `flashing` or `boot` command. It is not
a recovery demonstration and does not boot NixOS.

[[result]]
== Result (2026-10-15)

The owner started the entry; a watcher had already started the helper's
observation step with a 600-second wait and ran the return step as soon as
observation completed. Each of the four questions was answered once:

. *Entry.* `sudo /sbin/reboot bootloader` from an owner-run ADB shell shut the
  phone down and restarted it into fastboot mode.
. *Recognition.* With the phone on a direct USB port of the Mac, Platform-Tools
  `fastboot` listed exactly one device, without any port or cable change.
. *Variables.* 14 of 15 queries answered. `is-userspace` was `no`, so this is
  the bootloader's fastboot, not `fastbootd`. `unlocked` was `yes` and `secure`
  was `no`. `slot-count` was `0` and `current-slot` is unsupported, so the phone
  has no A/B slots. `boot` and `recovery` reported sizes of `2000000` and `dtbo`
  `800000`, hexadecimal without a prefix (32 and 8 MiB), all `raw data`,
  matching the GPT. `max-download-size` was
  `0x8000000` (128 MiB). Product `g61v71c2k_dfl_tee`, bootloader
  `g61v71c2k_dfl_tee-c94b80d-20210414101510-20230204181955`, baseband
  `MOLY.LR12A.R3.MP.V158.3.P1`.
. *Return.* `fastboot reboot` completed, and the phone started Ubuntu Touch
  normally. ADB reported `device` 191 seconds later, after the owner unlocked
  the screen; until then the phone's USB function offered only an RNDIS network
  interface.

The after-return baseline matched the earlier one: the same kernel, a boot
command line that differed only in three boot-timing values (`bootprof.*`), no
`/run/systemd/reboot-param`, a new boot ID and 100% battery. Of the three
failed units recorded before, two are periodic jobs that had not run again yet;
`console-setup` failed as before.

Owner-run normal-mode copies of the twelve unmounted control and calibration
regions before and after the trial were byte-identical except `expdb`, which
differed in 30 blocks of 4 KiB. Without an earlier pair of normal-mode copies,
this does not show whether fastboot entry, the restart itself or ordinary
operation changed it; see link:control-region-preservation.adoc[that record].

Not shown: that an ordinary reboot after the trial boots normally, how the
bootloader handles the persistent marker (the boot after `fastboot reboot` was
normal), repeatability, the physical fallback, rescue-image acceptance,
`fastboot boot` support or anything about NixOS.

== Purpose

Answer four questions about the installed bootloader on this phone:

. Does an orderly reboot with the `bootloader` argument reach bootloader
  fastboot mode?
. Does the Mac recognize that mode over USB?
. What do standard read-only `getvar` queries report, including whether this is
  bootloader fastboot or userspace `fastbootd`?
. Does the standard `fastboot reboot` command return to the existing Ubuntu
  Touch installation?

The answers decide whether a later, separately reviewed offline acquisition boot
is worth proposing. They do not establish rescue-image acceptance, temporary
boot support, writer quiescence or a restore procedure.

== Basis

* The installed `/sbin/reboot` is systemd `255.4-1ubuntu8.17`. Its exact-version
  source stores the `bootloader` argument before asking logind, and the ADB user
  lacks write access to that file, so an unprivileged request is predicted to
  fail first. The trial therefore uses the phone's existing sudo credential; see
  link:recovery-preparation.adoc#_installed_reboot_path_and_persistent_rtc_state[the reboot-path record].
* The pinned kernel maps that argument to the persistent RTC fast-boot marker
  and then resets. Whether the installed bootloader clears the marker is
  unknown, and it will not be determined by reverse engineering.
* Android properties report an unlocked bootloader (`flash.locked=0`, `orange`).
  This trial does not depend on that state because it sends no image.
* The Mac has Platform-Tools `37.0.1-15733141` (`adb` 1.0.41 and `fastboot`).

== Preconditions

All of these must hold, or the trial is postponed:

* The owner is present with the phone connected directly to the Mac by a
  known-good data cable, not through a hub.
* Battery at least 60%, and no system-image update in progress.
* A fresh private catalog pass has succeeded (done on 2026-10-15).
* A verified normal-mode link:control-region-preservation.adoc[control-region
  copy] exists (done on 2026-10-15).
* The owner has decided, before starting, the stop conditions below.

== Procedure

. *Baseline, normal mode, read-only.* Save privately: `adb -d get-state`,
  `uname -r`, `systemctl is-system-running`, `systemctl --failed --no-legend`,
  the battery capacity and `/proc/cmdline`. These are compared after return.
. *Entry, owner-run.* In a local Terminal:
+
[source,sh]
----
adb -d shell
sudo /sbin/reboot bootloader
----
+
The password is typed only at the phone's sudo prompt in that Terminal, never
in chat, a file or a command line. Expected: an orderly shutdown and a restart
into the bootloader's fastboot mode.
. *Recognition, read-only.* Within two minutes, run `fastboot devices`. Exactly
  one device must be listed; keep its serial private. Then query only:
  `product`, `version-bootloader`, `version-baseband`, `secure`, `unlocked`,
  `is-userspace`, `max-download-size`, `current-slot`, `slot-count`, and
  `partition-size:` / `partition-type:` for `boot`, `recovery` and `dtbo`.
  `is-userspace` is `yes` only in `fastbootd`. An unsupported variable is
  recorded as unknown, not retried another way.
. *Return.* Run `fastboot reboot`. Wait up to five minutes for `adb -d get-state`
  to report `device`.
. *After return, read-only.* Repeat the baseline and compare. Record the
  observed screens, timings and any difference. Optionally rerun the
  control-region reader (owner's sudo) and compare per-region hashes privately;
  its record explains what a difference does and does not show.

The `tools/observe-fastboot.py` helper runs steps 3 and 4 with exactly this
allowlist, fixed timeouts and private output; it refuses every other command.
It requires exactly one listed device, keeps its serial out of terminal output,
and writes one private record per step:

[source,sh]
----
python3 support/experimental-devices/unihertz-titan/tools/observe-fastboot.py observe \
  --output /absolute/private/new-fastboot-observation
python3 support/experimental-devices/unihertz-titan/tools/observe-fastboot.py return \
  --output /absolute/private/new-fastboot-return
----

Its nine synthetic tests use a fake executable. On 2026-10-15 it ran both steps
against the phone; see <<result,the result>>.

== Stop conditions and failure handling

[cols="2,3",options="header"]
|===
|Observation |Action
|The reboot command fails without restarting
|Stop. Record the error. Do not retry with `adb reboot`, D-Bus or other routes.
A stored `bootloader` parameter may remain in `/run/systemd/reboot-param`, so the
next reboot of any origin can enter fastboot; handle that with step 4.
|The phone restarts into Ubuntu Touch instead
|Stop and record. The marker may still be set; a later reboot may enter
fastboot, which is then handled with step 4.
|The phone shows a recovery screen
|Touch nothing except the option that reboots the system normally. Record it;
the installed recovery can write logs and is not presumed passive.
|Fastboot mode is shown but the Mac lists no device
|Try another direct port and cable for up to ten minutes. If still absent, go to
the physical fallback below.
|More than one device is listed
|Stop and disconnect other devices before any query.
|`fastboot reboot` returns to fastboot mode again
|Run `fastboot continue` once (the helper's `return --command continue`). If the
phone still does not boot Ubuntu Touch, stop and seek OEM guidance; issue no
other command.
|Ubuntu Touch does not finish booting after return
|Stop. Do not flash or erase. A boot rollback is a separate, later write that
requires its own authorization.
|Battery below 30% at any point
|Stop after returning, and charge in normal mode.
|===

*Physical fallback (unverified).* With the runtime configuration
(`ONEKEY_REBOOT_NORMAL_MODE=y`, `KPD_PMIC_LPRST_TD=0`), the pinned keypad driver
enables the PMIC power-key long-press reset at its 8-second setting while this
kernel runs. That is source and configuration evidence only, and the kernel is
not running in the bootloader, so the behavior there is unknown. Holding Power
until the phone restarts is the only remaining fallback, and it may land in
fastboot again. There is no verified emergency restore for macOS.

*Key entry (owner-observed, 2026-10-15).* Holding Volume Up while the phone
starts from the powered-off state opens the installed recovery, which showed
the stock Android "No command" screen; the owner returned with its normal
reboot option, and the next boot reported `androidboot.bootreason=PowerKey`.
The owner found no key combination that enters fastboot directly. The recovery
is the stock Unihertz Android 10 recovery (`QP1A.190711.020`, built
2022-11-21, `user/release-keys`); holding Power and tapping Volume Up shows its
menu. Its "Reboot to bootloader" entry reached bootloader fastboot
(`is-userspace: no`) on 2026-10-15, and the observation helper's `fastboot
reboot` returned to Ubuntu Touch. This gives a manual path into fastboot that
does not depend on Ubuntu Touch, as long as that recovery stays installed.

== Residual risks

* The bootloader's handling of the persistent fast-boot marker is unknown. The
  boot after `fastboot reboot` was normal, and an ordinary reboot during the
  later link:temporary-boot-trial.adoc[temporary boot trial] was normal too.
* The shutdown is the ordinary systemd reboot path with an argument. It does not
  prove clean filesystems or modem quiescence, the same as any reboot.
* The bootloader may update its own state in regions such as `para`, `expdb`,
  `boot_para` or `seccfg`. Repeat
  link:control-region-preservation.adoc[normal-mode copies] detect such changes
  without attributing them; across the 2026-10-15 trial only `expdb` changed.
* Mac recognition was shown once, on one direct port with one cable.

== What the trial can and cannot show

A successful run shows that this phone entered and left bootloader fastboot
once by this route and reported the recorded variables. It does not show
acceptance of an unsigned rescue image, `fastboot boot` support, offline
acquisition, a restore path or anything about NixOS. Keep raw output, serials
and screens private; publish only sanitized findings.
