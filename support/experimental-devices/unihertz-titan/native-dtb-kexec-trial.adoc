= Tree-replacing kexec trial

Status on 2026-10-16: *run once with the owner's explicit approval; all four
questions were answered yes. See <<result,the result>>.* Each repetition needs
the owner's explicit approval of this exact procedure.

The link:native-cpu-power-trial.adoc[CPU power-down trial] gave the working
environment's kernel CPU hotplug and kexec'd kernels with all eight CPUs, but
its tree-replacing kexec was refused by `titan-dtb-check`, which could not
list a kexec'd kernel's tree; the check now reads trees as `dtc` rewrites
them. This trial repeats that kexec through `kexec_file_load`, which leaves
the next kernel a tree of the kind that was refused, and from there runs the
tree-replacing path, `titan-kexec --dtb` through `kexec_load`, for the first
time anywhere, with a copy of that tree plus one property that nothing reads,
which must arrive in the next kernel. Before starting the loaded kernel, it
checks that kexec-tools placed every segment in ordinary memory, clear of
every reserved region. Being able to hand a kexec'd kernel a modified tree
is what makes kexec usable for trying device-tree changes without flashing.
The original recovery is then restored. Ubuntu Touch's boot and `dtbo`
partitions are never written, and Linux never sees the phone's storage.

[[result]]
== Result (2026-10-16)

The owner approved the procedure and ran the partition reads, the entries, the
Volume Up start and the unlocks; watchers ran the fastboot steps, the push and
the USB log, and the session ran over SSH from the Mac.

* *Preconditions and Part 1.* As before: battery full and charging, no update,
  empty recovery command directories, boot, recovery and dtbo identical to
  their preserved copies and no control region changed since the latest copy;
  `Writing 'recovery' OKAY`, and step 7 read recovery back as `73bd254c...`.
* *Question 1, yes.* SSH answered by 45 seconds of uptime, and `titan-session
  end-in 40` moved the end to 2445 seconds. All eight CPUs came up, the
  driver registered, the log was complete, and NixOS was `running` at 35 °C.
  The bootloader's tree listed cleanly (`fdtget -l` exited 0) and had no
  `/memreserve/` entry.
* *Question 2, yes.* `kexec_file_load` returned 0; the image's device left
  two seconds after `systemctl kexec` and was back four seconds later. The
  next kernel brought up all eight CPUs, with the first boot's
  reserved-memory lines and nodes, KASLR on and its code at `0x42800000`.
  Its tree was of the kind that had been refused: `fdtget -l` exited 1. It
  carried one `/memreserve/` entry, `0xfe200000` for `0xd31f1` bytes, for its
  initrd. About 20 seconds into that boot the device dropped off USB for two
  seconds and returned, like the earlier blips; the session carried on.
* *Question 3, yes.* The copy of that tree matched its record, `fdtput` added
  `titan,dtb-trial = "b"` at the root, and the two trees' `dtc` sources
  differed by that line only. The fixed `titan-dtb-check` accepted the tree,
  and `kexec_load` returned 0 with four segments: the kernel at `0x40000000`
  (41156608 bytes), the initrd at `0x42740000`, the tree at `0x42814000` and
  the purgatory at `0x42828000`, entered at `0x42828750`. kexec-tools noted
  that it could not open `/proc/kcore`, which only crash dumps need. The
  placement check passed: every segment lay in System RAM, clear of every
  reserved range, reserved-memory node and the `/memreserve/` entry. After
  `systemctl kexec` the device left within three seconds and was back 18
  seconds later, so the purgatory's uncached checks took about 14 seconds
  more than `kexec_file_load`'s path. The next kernel brought up all eight
  CPUs, with the first boot's reserved-memory lines and nodes, KASLR on, its
  code at `0x40000000` and both markers on its command line, and
  `/proc/device-tree/titan,dtb-trial` read `b`. Its tree differed from the
  one handed over only in `/chosen`: the new initrd's addresses and the
  command line, which kexec-tools writes with two empty strings after it.
* *Question 4, yes.* `titan-session end-in 1` at 81 seconds of uptime; the
  device left 74 seconds later, the preloader passed through, and Ubuntu
  Touch booted (`bootreason=reboot`). From Ubuntu Touch, `sudo /sbin/reboot
  bootloader` reached fastboot, the preserved original was written (`Writing
  'recovery' OKAY`) and Ubuntu Touch returned. The read-back found recovery
  `4dd1c1f7...`, with boot and dtbo unchanged throughout; of the control
  regions only `expdb` changed, as after every boot.

The session data, kernel logs and trees are in the private evidence
directory. This is the first tree-replacing kexec on the Titan: a kexec'd
kernel can be given a tree of our choosing, keeping the bootloader's reserved
memory, with all eight CPUs, so device-tree changes can now be tried without
flashing, each still with its own trial. Not shown: `kexec_load` with the
bootloader's own tree, a tree with real changes, `--nosmp` on the phone, or
suspend.

== Preconditions

As in the link:native-cpu-power-trial.adoc[CPU power-down trial]: the owner
present, a direct cable, battery at least 80%, no update pending, no recovery
command file, both private copies of the original recovery (`4dd1c1f7...`)
verified, and a normal-mode control-region copy right before the trial with

other than step 9 and the rows below.

== Procedure

*Part 1: write the image.* Steps 1 to 7 of the
link:repo-kernel-trial.adoc[repository-kernel trial], with `--profile
ram-nixos-6` and the image
`native-ram-image-v7/UNTESTED-UNSIGNED-native-ram.img`; step 7 must read
recovery back as `73bd254c...`, with boot and dtbo unchanged.

*Part 2: run the session.*

[start=8]
. *Listen:* start `tools/ram-nixos.py` as its own job, which reports as soon
  as SSH answers, with the private copy of the store squashfs, its pinned size
  and SHA-256, a new private output directory and the dedicated key; and a
  watcher that records every USB device change and whether Ubuntu Touch or
  fastboot appears after the image.
. *Start, owner-run:* keep the cable connected, power the phone off from
  Ubuntu Touch, hold Volume Up and press Power, and release both once the
  unlocked-state warning appears; allow the accessory if macOS asks. No
  confirmation is needed: the session starts when SSH answers.
. *Session:* at once and only once `titan-session end-in 40`; then the
  records of the link:native-kexec-trial.adoc[kexec CPU trial], including
  the driver's registration, a copy of `/sys/firmware/fdt` with its SHA-256,
  its `/memreserve/` entries, and the exit status of `fdtget -l
  /sys/firmware/fdt /`. Read-only throughout: nothing written in sysfs,
  debugfs or configfs, and no debugfs register dumps.
. *Kexec A, `kexec_file_load`:* as in the CPU power-down trial: copy the
  payload's `Image` and `initramfs.cpio.gz` into `/run/kexec`, run `strace -f
  -e trace=kexec_load,kexec_file_load titan-kexec /run/kexec/Image <its
  SHA-256> /run/kexec/initramfs.cpio.gz <its SHA-256> titan_kexec=a`, which
  must show `kexec_file_load`, then `systemctl kexec`, and once the image's
  USB device has left `tools/ram-nixos.py --wait 900` as its own job with a
  new output directory. Expected: the device returns within about a minute,
  stage 0 takes the push and SSH answers; then the records, which must show
  eight CPUs and the first boot's reserved-memory lines and nodes.
. *Kexec B, `kexec_load` with a modified tree:* only if the system from kexec
  A runs, answers SSH, has all eight CPUs and the first boot's reserved
  memory, with at least ten minutes left to its session deadline and the CPU
  below 55 °C.
** Copy the payload again, and this kernel's tree with `cp /sys/firmware/fdt
   /run/kexec/fdt-b.dtb`, which must match the saved record; add the
   property with `fdtput -t s /run/kexec/fdt-b.dtb / titan,dtb-trial b`,
   check with `fdtget` that it reads `b`, and check that the trees' `dtc`
   sources differ only by that line.
** Run `titan-kexec --dtb /run/kexec/fdt-b.dtb <its SHA-256> /run/kexec/Image
   <its SHA-256> /run/kexec/initramfs.cpio.gz <its SHA-256> titan_kexec=b`
   under the same `strace`, which must show `kexec_load` and its segments,
   and `/sys/kernel/kexec_loaded` must read `1`.
** *Placement check:* for an ordinary `kexec_load` the kernel leaves it to
   kexec-tools to avoid reserved memory. Each segment, from `mem` to `mem +
   memsz`, must lie within one `System RAM` range of `/proc/iomem` read after
   the load, and overlap none of its `reserved` ranges, the reserved-memory
   nodes' `reg` ranges or the tree's `/memreserve/` entries; overlapping the
   running kernel itself is normal. If any segment fails, do not start it:
   go to the end step, whose restart discards the loaded kernel.
** Then `systemctl kexec`, `tools/ram-nixos.py --wait 900` as its own job
   once the device has left, and the records, which must show eight CPUs,
   the first boot's reserved-memory lines and nodes, `/proc/device-tree/
   titan,dtb-trial` reading `b`, and a tree that differs from `fdt-b.dtb`
   only in `/chosen`.
. *End:* `titan-session end-in 1`; the session deadline must restart the
  phone into Ubuntu Touch within about two minutes. Only if it has not after
  three minutes, `titan-session end`.

*Part 3: restore.* From Ubuntu Touch, `sudo /sbin/reboot bootloader`
(owner-run); then, as in the earlier trials, write the preserved original
with the `original-recovery` profile, return, and read recovery back as
`4dd1c1f7...`, with boot and dtbo unchanged.

*Part 4: compare.* A normal-mode control-region copy after Part 3, compared
with the one from step 2 (`expdb` changes on every boot).

== Residual risks

* The tree-replacing path has not run anywhere: kexec-tools places the
  segments itself, which the placement check verifies before they are
  started, adjusts the given tree's `/chosen`, and its purgatory checks the
  segments' SHA-256 with the caches off before starting the kernel. A fault
  there, or a mismatch, on which the purgatory loops instead of failing,
  hangs the phone with no deadline running.
* `titan-dtb-check` does not compare the trees' `/memreserve/` entries. The
  bootloader's tree has none; the tree from kexec A has one, for its own
  initrd, which `fdtput` keeps, so kexec B's kernel reserves that stale
  region too. Trees with real changes need the check to compare them.
* Each kexec makes the driver's firmware calls for cpu1 to cpu7 in the old
  kernel's shutdown, without any guard, as in the CPU power-down trial's
  kexec, which they passed with this kernel.
* `titan-dtb-check` keeps the reserved memory and memory nodes as the
  running tree has them; the added property is one that nothing reads, so
  kexec B changes nothing else. A tree with real changes needs its own
  trial.
* As in the earlier trials: devices left in states the next kernel does not
  expect (the USB gadget is detached before each kexec), and sessions with no
  frequency scaling, throttling or charger driver.

== What this can and cannot show

Success shows that a kexec'd kernel can be given a tree of our choosing,
keeping the bootloader's reserved memory, with all eight CPUs, which is the
basis for trying device-tree changes such as the display or I2C without
flashing. It does not show `kexec_load` with the bootloader's own tree, a
tree with real changes, `--nosmp` on the phone, or suspend.
