= I2C bus scan trial

Status on 2026-10-16: *run once with the owner's explicit approval; all five
questions were answered, and two devices answered the scan. See
<<result,the result>>.* Each repetition needs the owner's explicit approval
of this exact procedure.

The link:native-i2c-trial.adoc[first I2C bus trial] enabled the sensors' I2C
controller at `0x11011000` in a kexec'd kernel, which probed as `i2c-1`, but
its pin gate read the bus pins' mode as 9 where it required 1, and the scan
was skipped. The register holds 9 in both kernels: MediaTek's MT6771 pin
driver reads a mode of 8 or more as that value minus 8, so 9 is function 1,
`SDA1` and `SCL1`, as under Ubuntu Touch. This trial repeats the first one
with that rule in the gate, the debugfs path this kernel uses, and a check
that the bus lines are released after the scan. Everything else is
unchanged.

== Result (2026-10-16)

The owner ran the two step 2 copies, then approved the procedure, and ran the
entries, the Volume Up start and the unlocks; watchers ran the fastboot steps,
the push and the USB log, and the session ran over SSH from the Mac.

* *Preconditions and Part 1.* The step 2 copies found boot, recovery and dtbo
  identical to their preserved copies and no control region changed since
  the latest copy; the baseline, taken after them, found the battery full and
  charging, no update pending and empty recovery command directories, with
  Ubuntu Touch's update service idle after System Settings had been opened.
  `Writing 'recovery' OKAY`, and step 7 read recovery back as `07070c4d...`.
* *Question 1, yes.* As in the first run: the tree copy differed from the
  running tree in the node's `status` line only, `kexec_load` placed the
  kernel at `0x42400000` and the rest just above, the placement check
  passed, and the next kernel brought up all eight CPUs with the first
  boot's reserved memory, a tree that read `okay` for the node and differed
  from the one handed over only in `/chosen`, and exactly one adapter,
  `i2c-1`, the controller at `11011000`.
* *Question 2, yes.* GPIO81 and GPIO84 read mode 9, function 1, with their
  input level high and pull-ups on; GPIO87 and GPIO88 read function 1 and
  GPIO163 and GPIO164 function 2.
* *Question 3: `0x2c` and `0x60`.* `i2cdetect -y -r 1` finished in 0.11
  seconds with exit status 0, while the controller's interrupt count rose
  from 0 to 222, about two per address: every address was answered or
  refused by the bus, and the table is a real result. Two addresses
  answered, `0x2c` and `0x60`, and none of the vendor overlay's `0x0c`,
  `0x15`, `0x32`, `0x48` and `0x51`. The kernel logged no I2C error.
* *Question 4, yes.* After the scan GPIO81 and GPIO84 again read input
  level high: no device held the bus, and no power-off was needed.
* *Question 5, yes.* `titan-session end-in 1` at 104 seconds of uptime; the
  device left 83 seconds later and Ubuntu Touch booted (`bootreason=reboot`).
  From Ubuntu Touch, `sudo /sbin/reboot bootloader` reached fastboot, the
  preserved original was written (`Writing 'recovery' OKAY`) and Ubuntu Touch
  returned. The read-back found recovery `4dd1c1f7...`, with boot and dtbo
  unchanged throughout; of the control regions only `expdb` changed, as after
  every boot.

Ubuntu Touch's kernel is a sensor-hub build: its configuration has
MediaTek's hub drivers for the accelerometer, light and proximity sensor,
gyroscope and magnetometer and no driver for any sensor chip, since the
sensor co-processor's firmware drives the chips. The overlay's sensor list is
a reference board's, not this phone's fitting. Identifying the two devices
needs reading an identification register from each, which first writes a
register pointer and so needs its own trial: the
link:native-i2c-id-trial.adoc[I2C device identification trial]. Unverified, by address alone:
`0x60` is where Capella's CM36686 family of light and proximity sensors
answers, and `0x2c` where QST's QMC6308 magnetometer does.

The session data and kernel logs are in the private evidence directory. This
is the native kernel's first working I2C bus: a controller enabled through a
kexec'd tree, its pins in their I2C function, and two devices answering a
read-only scan. It does not show which devices they are, any device driver,
or the other buses.

== Basis

As in the link:native-i2c-trial.adoc[first I2C bus trial]: the same image,
flash profile `ram-nixos-8`, padded `07070c4d...`, with the same kernel,
stage 0, store and kexec payload, and the same bus map. The first run showed
the kexec, the adapter and the pins as this trial expects them: GPIO81 and
GPIO84 at mode 9, GPIO87 and GPIO88 at 9 and GPIO163 and GPIO164 at 10, that
is functions 1, 1 and 2, with both bus lines high and their pull-ups on.

* *MediaTek's rule.* Both kernels read the same 4-bit mode field. MediaTek's
  MT6771 driver (`pinctrl-mt6771.c`, `nfuncs = 8`) prints a mode of 8 or
  more as that value minus 8 (`pinctrl-paris.c`), and Ubuntu Touch's GPIO
  table shows these pins at mode 1; mainline's MT8183 data sets no
  `nfuncs` and prints the raw value.
* *The pin readout.* Each line of
  `/sys/kernel/debug/pinctrl/10005000.pinctrl-pinctrl_paris/pins` gives, after
  the pin's zero-padded number, the mode, then the direction, the output
  level and the input level, each one digit (`pinctrl-paris.c`).

== Procedure

As in the link:native-i2c-trial.adoc[first I2C bus trial], steps 1 to 13
and Parts 1, 3 and 4, with these changes to step 12 and Part 4:

* *Pin modes, reading debugfs:* save the lines for GPIO81, GPIO84, GPIO87,
  GPIO88, GPIO163 and GPIO164 from `/sys/kernel/debug/pinctrl/
  10005000.pinctrl-pinctrl_paris/pins`. A pin's function is its mode, or its
  mode minus 8 when the mode is 8 or more. GPIO81 and GPIO84 must be in
  function 1, and the other four must not be in function 3; otherwise skip
  the scan and go to the end step.
* *After the scan:* read the same six lines again. GPIO81 and GPIO84 must
  show input level 1: a 0 means a device holds a bus line low.
* *Part 4:* the Ubuntu Touch sensor check is replaced by the line check
  above, since this Ubuntu Touch offers no automatic brightness. If a line
  read 0, power the phone fully off once after Part 3, which removes a
  device's always-on supply, before relying on its sensors.

== Stop conditions

The first I2C bus trial's table applies, with its pin row replaced and one
row added:

[cols="2,3",options="header"]
|===
|Observation |Action
|GPIO81 or GPIO84 is not in function 1, or an alternative pin is in function
3, by MediaTek's rule
|Record the pin lines and go to the end step without the scan.
|After the scan, GPIO81 or GPIO84 shows input level 0
|A device holds the bus. Record the lines, run no further I2C command, go to
the end step, and after Part 3 power the phone fully off once.
|===

== Residual risks

As in the first I2C bus trial, and this time the scan runs: it sends one read
to each address from `0x08` to `0x77` on a bus with five sensors and writes
nothing, since this controller cannot send a write without data. A read that
times out ends without a stop condition, and the driver has no bus recovery;
the line check after the scan shows whether that left a device holding the
bus.

== What this can and cannot show

Success shows which of the vendor's sensors answer on the native kernel's
first working I2C bus, the start for adding their drivers. It does not show
any device driver, the other buses, the touch panel, the keyboard or the
display.
